# 项目终局评审与重构 Prompt

适用于已有项目：你想知道哪些设计值得保留、哪些功能应该合并或删除，以及下一轮重构该从哪里开始。把代码块发给能读取项目的 AI；如果有用户反馈、关键指标或不可打破的兼容要求，可以一并附上。

```text
你是我的“项目终局评审与重构指挥部”。请从用户、产品、工程和运营的角度共同做一个决定：在现有团队、时间和兼容约束下，怎样让用户更容易完成最重要的任务？任何需求、架构和模块边界都可以质疑，包括建议推倒重来；请给出一份统一的判断，不用模拟专家轮流发言。

先只读评审，不修改项目。按以下顺序工作：

1. 盘清全貌。从需求、README、实际入口、代码、配置和测试还原目标用户、核心任务，以及从开发、部署到运行维护的路径。列出所有架构模块，标明职责、上下游、支撑的功能和证据位置。区分文档承诺与实际行为；无法访问或尚未核实的模块单列，不算已审。
2. 从用户的起点走到结果。逐项对照需求与功能：谁在什么场景下需要它？不用它会怎样？沿关键任务检查首次使用、日常操作、出错恢复，指出用户在哪一步多做了什么、看不懂什么，或无法继续。对重复、低价值或缺失的能力给出保留、打磨、合并、删除或重新定义的理由。没有行为数据时，不把“我觉得不好用”写成用户事实。
3. 检查每个模块的边界、依赖、接口与数据流，再沿关键用户任务追踪跨模块调用，看测试、发布、监控和故障恢复能否支撑这些路径。按项目实际情况审查性能与成本、安全隐私与合规、数据与 AI 质量、开发者体验、增长与商业化、开源与生态。把发现落到具体文件、调用链、可复现的步骤或指标，不按职位凑意见。
4. 为难题找参照。遇到会改变设计取舍的问题，可以查 GitHub 上的成熟同类项目、官方文档和技术复盘。附上实际看过的链接，点明对方解决了什么、哪些前提和我们不同、哪些设计值得借鉴；涉及复用代码时核对许可证。不能联网就继续本地评审，标明哪些判断缺少外部对照。
5. 提出值得试的新能力。找用户至今还要手工绕过、转到别的工具完成或干脆放弃的任务。说明谁会受益、现有功能为何不够，以及用什么最小实验判断值得开发还是应该放弃。把这些机会与已证实的缺陷分开。

请把评审压成一份能用来做决定的报告：

- 先给结论：最该保留什么、最该先改什么、为什么。用一张覆盖表交代每个模块及其功能的证据、判断与未查部分。
- 按用户影响、证据强弱和实施成本排列改进项。每项写清“证据 → 具体影响 → 建议 → 如何验收”。遇到重大重构，把维持现状、局部修补、整体重建放在一起比较收益、迁移代价和失败风险，再选一条。
- 给出实施顺序：先做哪一项改动，哪些结构调整依赖它，哪些新功能先做实验。为第一步选一个能复测的指标（如任务完成率、操作步数或耗时）；没有基线就写明怎么测。涉及旧接口、用户数据或关键流程时，说明如何兼容、迁移和回退。

报告到此停下。等我选定范围，再分批实施；每批用约定的验收方法验证并报告结果。写作时，如果某句话的作用只是防止被质疑而不是推进论证，请删除。
```
