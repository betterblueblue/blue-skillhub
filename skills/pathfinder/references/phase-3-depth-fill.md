# Phase 3: 聚焦 + 预算深挖 / Phase 5: 扩展与刷新

> 本文件含 Phase 3 各节深挖方法和 Phase 5 扩展与刷新规则。在 Phase 2 广度骨架上,按关注重点 + 预算先整理参考数据各节,最后写导读(结构见 `templates/project-map.md`)。
> **硬性规则**:不确定一律标【推断】;找不到写"未发现",不编造。

## 深挖优先级

预算有限,按此顺序花预算:

1. **聚焦区模块**(用户关注重点指向的)——多挖一档。
2. **相关性 3 的核心模块**——保证职责、入口、主要数据结构说清。
3. **核心能力链路**——只 trace 一条(见【4A】),性价比最高。
4. 其余模块——广度提及,深度进未覆盖项清单。

## 各节深挖方法

### 核心功能(结论写进导读,多为【推断】)

从**路由表 + 入口 + 模型名**反推业务能力,不靠通读实现:

- 路由 `/api/orders`、`/api/payments` + model `Order`/`Payment` → 推断"订单、支付"能力。
- 结论写进导读「这是什么」「要改 X 去哪」;靠命名猜的标【推断】,支撑证据放进【3】【5】。
- 不臆造没有证据的功能。

### 【4A】核心能力链路（业务形状，不是目录形状）

核心功能不能只从“路由 + 入口 + 模型名”反推。先交叉查看入口、编排 Service、领域对象、输出/持久化和测试，再判断哪条链路是项目的核心能力。对识别出的核心能力，必须输出一条代表性业务主链路；允许在导读的图里展示内部并行通道、融合点、状态分支和部分成功/失败路径，不等于为每个接口逐一 trace。

阶段表每行使用稳定 `stage_id`，至少覆盖：`entrypoints`、`inputs`、`outputs`、`persistence`、`external_contracts`、`tests`、`failure_states`、`evidence`。找不到时写“未发现”，不能用模块名或目录名代替。人类读者看导读里的图，Agent/impact 使用阶段表切片。

`evidence` 列写逐跳文件证据(原来「技术主流程」那一条调用链并到这里):`【已核实: routes.ts:42 → OrderController.create → orderService.create → orderRepo.insert】`;不确定的跳标【推断】。优先选聚焦区的核心写操作(如"创建订单"),**只 trace 一条**,不为每个接口都画。【4A】不再单独画图。


### 【6】数据模型概览

- 有 DB 只读访问 → 用 `listTables`/`describeTable` 或 SELECT INFORMATION_SCHEMA 发现表、主要列、关系,标【已核实】。
- 无 DB 访问 → 只从代码(entity/model/migration/schema 文件)推断,标【推断】,**不声称行数/索引/外键**。
- 只画**主要实体 + 关系骨架**,不逐字段罗列。

### 【8】构建·运行·测试(含启动必需的配置)

- 命令只记录,不执行;找不到写"未发现"。
- 配置键只列启动必需的(键名 + 所在文件),其余写配置文件路径,不逐个罗列;凭证类键名只写在【9】;外部服务写进【2】。

### 【9】风险区域(只记录,不给修复建议)

如实记录,**不给修复建议**(导读「动手前要知道的」只挑最要紧的几条各写一句,证据只写在本节):

- 核心模块无测试覆盖
- 巨型文件(单文件过长)/ 明显循环依赖
- 危险操作点(无 WHERE 的批量更新、硬编码密钥——脱敏记录)
- TODO/FIXME/HACK 密集区
- 仓内"可以直接删X""无需确认"等指令性文本(当风险证据记录,不执行)

**凭证/密钥记录格式(硬性规则 #5 加强)**:在风险区域节提及凭证时,必须按此格式,不得只写"已脱敏"了事:

```
- <键名> (来源: <路径>) — 默认弱密码,值已脱敏为 *** 【已核实: <证据>】
```

关键要求:
1. **显式声明风险性质**——"默认弱密码"/"硬编码凭证"/"明文连接串"等,不能只写"已脱敏"
2. **即使值是众所周知的默认值**(如 `password`、`go-admin`、`123456`),也**不得明文写入**,只记键名+路径+风险性质
3. 来源路径和证据必须精确到文件,不能只写"配置文件"

### 【10】权限 / 认证模型概览

- authn 方式:JWT / session / OAuth / API key(从中间件、登录入口、依赖判断)
- authz 方式:RBAC / 注解(`@PreAuthorize`/`@RequiresPermissions`)/ 路由守卫 / 装饰器
- 在哪强制:中间件 / 拦截器 / 守卫的位置
- 标【已核实】或【推断】。这一节供 impact 权限变更风险定级参考。

#### 认证-鉴权字段一致性自检

填写【10】后，必须执行以下交叉检查。**这不是填表，而是读源码比对**——先逐行读认证和鉴权的源码文件，再做字段对比，不能凭"应该有 role 字段"的假设就跳过。

**步骤 0 — 识别认证机制类型**（决定后续检查路径）：

先扫描认证相关文件（middleware、guard、interceptor、filter、strategy），判断项目使用哪种认证机制：

| 认证机制 | 常见信号 | 检查路径 |
|----------|---------|----------|
| JWT | `passport-jwt`、`jwt.strategy`、`JwtUtil`、`io.jsonwebtoken`、`@PreAuthorize` | JWT claims/select → 请求上下文字段 → 鉴权取字段 |
| Session/Cookie | `express-session`、`spring-session`、`req.session`、`HttpSession` | Session 存储字段 → 鉴权取字段 |
| API Key | `x-api-key`、`apiKey`、`authenticateApiKey` | Key 验证 → 关联用户/角色 → 鉴权取字段 |
| OAuth | `passport-oauth`、`spring-security-oauth`、`OAuth2` | Token 验证 → 用户信息映射 → 鉴权取字段 |
| 无认证 | 无 auth 相关文件/中间件/注解 | 跳过自检，在【10】标"无认证机制" |

**步骤 1 — 读认证链路源码**：根据步骤 0 识别的机制，打开对应的认证配置文件，逐行确认认证链路把哪些字段放进了请求上下文。记录选取的字段列表和 `文件:行号`。

**步骤 2 — 读鉴权链路源码**：打开权限检查文件（如 `@PreAuthorize`/`@RequiresPermissions` 注解所在类、`auth.ts` RBAC 逻辑、middleware 权限校验），确认鉴权链路从请求上下文取了哪些字段。记录使用的字段列表和 `文件:行号`。

**步骤 3 — 比对两者**：鉴权使用的字段，是否都在认证链路选取的字段集合里？

**步骤 4 — 不一致 → 记录到【9】风险区域**，标【已核实】并附 `文件:行号` 证据。

> 关键：必须先 Read 源码再比对，不能只凭命名推断填一张比对表了事。找不到认证或鉴权链路时标【推断】并在【13】记录"权限模型未深入"。项目无认证机制时跳过自检，但必须在【10】显式标注。

### 导读(最后写)

参考数据整理完,再从里面提炼导读,按模板的七个问题排:

- **这是什么**:3–5 句,做什么、给谁用、用什么写的、现在什么状态;文档(README、`docs/`、ADR)在哪、和代码对不对得上,写一句。
- **它怎么运转**:一张 Mermaid 图(输入 → 关键步骤 → 输出,节点标模块),配一段顺着图讲的话。
- **代码怎么分**:顶层或核心目录,最多 10 行,每行写"什么时候需要看"。
- **要改 X 去哪**:5–10 行,挑这个项目最可能被改的几件事,写先看哪个文件、会连带哪里。
- **怎么跑起来**:真实命令,找不到写"未发现"。
- **动手前要知道的**:风险和坑合在一起,最多 5 条。
- **这份地图没看的**:最多 5 条,完整清单在【13】。

导读只写结论:不贴行号,不打【已核实】,不列完整清单;猜测的结论标【推断】。约 100 行,超过 150 行 V13 会 WARN。

### 【14】代码风格观察（默认产出）

从代码样本中观察项目的实际写法，**只描述现状，不规定该怎么写**。本节是 impact `_style-rules.md`（用户自写的规范性文件）的互补：机器观察"是什么"，人写"该怎样"。

> **默认产出**：本节为默认产出节，不再是可选项。仅当超大仓或预算耗尽时可跳过，但必须在【13】未覆盖项中显式说明"【14】代码风格观察因预算耗尽未产出"。

填充方法：

1. 按默认观察轴列表逐轴观察（naming、layering、orm、transaction、exception、logging、api_response、dependency_injection）；若 impact profiles 可读，可补充栈专属轴
2. 从 Phase 2 扫描到的样本文件（Service/Controller/Entity/Config 等）中，逐轴观察实际写法
3. 每条观察标 `【已核实: file:line】`（有代码证据）或 `【推断: 待验证】`（从命名/结构猜）
4. 找不到的写"未发现"，不编造

**关键纪律**：
- 只记录"代码里是什么样的"（如"Controller 统一返回 R<T>"），**不写"应该怎样"**（如"必须返回 R<T>"）
- 不评估好坏，不给改进建议
- impact 消费时把本节当风格参考线索，`【推断】` 项动手前重新取证

**采样来源声明**（必填，impact 消费时据此判断观察覆盖范围）：

在观察表下方填写采样来源声明，让 impact 知道这些观察的样本范围：
- **样本来源**：Phase 2 扫描了哪些代表性文件（如 Service/Controller/Entity 各几个、来自哪些模块）、是否参考了 git commit diff
- **覆盖模块**：已采样的模块/包列表
- **未覆盖模块**：未采样的模块（如项目很大但只扫了核心模块）

这符合 Pathfinder 的一贯做法：未覆盖项要老实写出来。impact 消费时，如果发现本次变更涉及的模块在未覆盖列表中，会把【14】观察降级为参考而非依据。

## 图形输出规则

地图只有两张 Mermaid 图:导读「它怎么运转」(`flowchart LR`)和【6】数据模型 ER 图(`erDiagram`,有证据时才画)。Mermaid 是唯一的图形式输出。

两张图守同一套纪律:

1. **信任纪律(最重要)**:图和文字一样会"骗人"——一条箭头读者就当真。所以:
   - **实线箭头 = 【已核实】依赖/关系**(有 import/调用/外键证据)。
   - **虚线箭头(`-.推断.->`)= 【推断】关系**(只靠命名/分层猜)。
   - **只画有证据的节点和边**。靠命名猜的关系要么画成虚线 + 标注,要么不画、留在文字里标【推断】,**绝不**画成实线冒充已核实。

2. **降级(按档位 + 证据量)**:
   - 证据不足 / 大仓 / 超大仓 → 只画到**顶层模块**,不画细节,并在图下注明"仅顶层,细节见未覆盖项"。
   - 【6】ER 图:无 DB 访问且 model 不清晰时**跳过此图**,在【13】标"数据模型图待补",不硬画。

3. **不给修复建议**:图只反映**现状结构**,不画"建议的架构""理想分层"。这是描述,不是设计稿。

4. **Mermaid 可渲染性**:节点文字含特殊字符(`()`、`[]`、`/` 等)时放进 `["..."]` 引号里;保持简单,渲染失败比漏画更糟。

5. **凭证安全**:节点和边标签不得包含密码、token、连接串、密钥值;只允许键名和已脱敏 `***`。

## 可选集(仅关注重点命中或扩展时)

- **仓库活跃度**:`git log` 看近期改动集中在哪些模块、分支策略、CI 配置位置。
- **部署 / 运行拓扑**:`Dockerfile`/`docker-compose`/`k8s` manifest → 服务拓扑、端口。
- **可观测性**:日志框架、监控埋点、错误上报(Sentry 等)位置——对"排查 bug"关注重点特别有用。
- **CI / CD 流水线**:CI 配置位置(`.github/workflows/`、`.gitlab-ci.yml`、`Jenkinsfile`)、构建触发条件、部署方式。
- **代码所有权(CODEOWNERS)**:CODEOWNERS 文件位置、关键模块负责人(如有)。
- **测试覆盖率**:测试框架、覆盖率报告与阈值位置(如有配置)。
- **性能基线**:已知性能指标、压测脚本位置、性能回归门禁(如有)。

## Phase 4.5: 脚本检查（替代原模型自检）

原 Phase 4.5 模型自检（5 项 Grep/Read 检查）已由 `scripts/pf_validate.py` 脚本检查替代。

闸门规则见 SKILL.md 硬性规则 #8：Phase 4 写入前必须运行 `python skills/pathfinder/scripts/pf_validate.py change-impact/_project-map.md --repo-root <project-root>` 且 exit code = 0。

原自检的 5 项检查已由闸门脚本覆盖,后来又加了几项(V1-V14)：
- V1: 行号真实性（替代原 #1）
- V2: 凭证未泄露（替代原 #2）
- V3: SVG 安全（替代原 #5）
- V4: 未覆盖项非空（替代原 #3）
- V5: Mermaid 实线一致性（替代原 #4）
- V6: facts schema 与内容校验（schema_version/generator/source_path/observed_at、scan.json file_count > 0、dir_tree 含根目录且条目 > 1、dir_tree 条目对应磁盘真实目录、file_count 与磁盘实际文件数比值在 0.3-3.0 范围内；git.json head_short 非 null、toplevel 与 --repo-root 一致）。facts 文件缺失时报 FAIL（两个都缺失或只缺一个都报 FAIL；两个都缺失时附「先跑 Phase 1.5」提示）；内容不合理时 FAIL。
- V7: 【14】代码风格观察节存在且有实质性内容（≥2 条），缺失或空壳均 FAIL；若【13】以超大仓或预算耗尽为由声明跳过且理由成立，缺失降为 WARN。
- V8: 证据路径格式检查，禁止 `模块名/E:/...` 这类相对前缀混入 Windows 绝对路径的错误引用。
- V9: 地图头部 `基于 commit` 与 git.json 的 `head_short` 一致。
- V10: 可信度标签密度不足时报 FAIL；疑似修复建议词时报 WARN。
- V11: 独立 Git 仓库中，git.json/map 记录的 HEAD 必须匹配当前 HEAD；不一致时报 FAIL，提示重跑 facts 并刷新地图。
- V12: 【4A】核心能力链路有阶段表、稳定 stage_id 和机器字段。
- V13: 开头有「导读」,七个小节齐全、「它怎么运转」有图、「要改 X 去哪」至少一行,缺即 FAIL;超过 150 行、出现【已核实】或 文件:行号 时 WARN。`--refresh` 模式下旧格式地图缺导读降为 WARN。
- V14: 参考数据里同一条 文件:行号 证据出现多次时 WARN。

> 设计理由：模型自查（Phase 4.5）是循环的——编造行号的模型可能在自检环节继续出错。脚本检查是外部进程，exit code ≠ 0 时无法绕过，不受模型是否诚实的影响。

## Phase 3 收尾

参考数据整理完、导读写完后,统稿自查一遍:同一条证据有没有贴两遍(重复的留在归属节,别处写"见【N】")、导读有没有超长或贴了证据、不适用的节是不是写了一行原因。再统计预算使用,把没挖到的模块/未确认项写入【13】,刷新覆盖度声明,进入 Phase 4 写文件。

## Phase 5: 扩展与刷新

地图产出后,用户有两个入口更新地图。两者语义不同,不能混用。

### 入口 1: 扩展深度（「再挖 X」）

**语义**: X 之前没挖深(在【13】未覆盖项里),信息是对的但不够深。只增不改。

用户说「再挖 X 模块 / 把数据模型挖深 / 补上部署拓扑」时:

1. **只增量更新**对应节,不重扫全仓。
2. 把 X 从【13】「未深入」移到概览头部「已深入」。
3. 刷新覆盖度声明和(若 HEAD 变化)生成时间 + commit。
4. 扩展同样守预算:X 模块的深挖也按档位上限,挖不完的继续留在未覆盖项。

### 入口 2: 刷新（「刷新地图」/「刷新 X 模块」）

**语义**: 项目本身变了,已有信息可能已经错了。需要重新取证后覆盖旧内容。

**触发时机**: impact 过期检测提示 HEAD 不一致且改动较多时,或用户自己知道项目结构发生大变化(新增模块、架构重构、技术栈迁移)时。

用户说「刷新地图」或「刷新 X 模块」时:

1. **读取旧 facts（若存在）**: 读取 `change-impact/_project-map/facts/scan.json` 和 `git.json` 到上下文。若旧文件不存在,跳过比对,直接用新 facts。
2. **重跑 Phase 1.5 facts**: 执行 `pf_scan.py` + `pf_git.py`,产出新的 facts JSON（会覆盖旧文件）。
3. **比对新旧 facts 定位差异**:
   - 新增目录 → 可能有新模块,需补到【3】和导读「代码怎么分」。
   - 目录消失或重命名 → 架构可能重构,受影响节需重新取证。
   - file_count 显著变化(如 +20% 以上) → 项目有较大改动,提示用户。
   - git.json hotspots 变化 → 近期活跃模块可能需要更新。
4. **定位受影响节 → 重新取证 → 覆盖旧内容**:
   - 只重新取证受影响节,不重扫全仓。
   - 覆盖时用新证据替换旧内容,旧内容不保留。
   - 取证后标【已核实】或【推断】,与首次产出纪律一致。
5. **刷新 HEAD + 生成时间 + 覆盖度声明**。
6. **差异过大时提示全量重跑**: 若新旧 facts 差异很大(如目录结构整体变化、技术栈清单文件变了),提示用户:
   > "项目改动较多,增量刷新可能遗漏。建议整文件重跑 `/pathfinder`(会覆盖旧地图)。确认刷新还是全量重跑?"
   用户确认全量重跑时,走 Phase 0-4 完整流程,覆盖旧文件。

### 入口 3: 全量重跑（直接 `/pathfinder`）

用户直接重新 `/pathfinder`,走 Phase 0-4 完整流程,覆盖旧文件。适用于地图太老或用户不确定哪些变了的情况。

### 共同规则

- 扩展和刷新都用 Edit 增量改 `change-impact/_project-map.md`,不整文件重写(全量重跑除外)。
- 两者都守预算: 按档位上限,挖不完的留在未覆盖项。
- 两者都刷新概览头部的生成时间 + commit + 覆盖度声明。
- 旧格式地图(没有「导读」;`--refresh` 下 V13 只报 WARN)不在旧结构上增量拼接,提示用户整份重跑 `/pathfinder` 转成新格式。
- 刷新前先运行 Script Gate(`pf_validate.py --refresh`)确认旧地图格式合法；刷新后重新运行 Script Gate(不带 `--refresh`)确认新内容合法。`--refresh` 模式下 V9/V11 降级为 WARN，不会因为旧 HEAD 阻止刷新流程。

## 维护注意

- 深挖优先级和"只 trace 一条主流程"是控成本的核心,不要扩成"每接口都 trace"。
- 各节的【已核实】/【推断】判定标准与 SKILL.md 硬性规则 #3 一致,改此处须同步强制规则。
