# Pathfinder 地图质量检查清单

> 适用文件：`change-impact/_project-map.md`
>
> 地图的两个核心作用：
> 1. 让人快速看懂「这项目是干啥的、核心功能是什么」
> 2. 给 agent/impact 提供上下文，在现有架构 + 现有风格轨道上可控迭代
>
> 评级：每项标 **必过** / **建议** / **加分**；人类层和 Agent 层各有总评（达标 / 基本达标 / 不达标）。
> 自动检查由 `pf_validate.py` 执行，人工评审用本文件的 §一 + §二。

---

## 一、给人看的检查（导读测试）

测试方法：只读「## 导读」，不翻参考数据、不问 AI 补充。

| # | 检查项 | 级别 | 通过标准 |
|---|--------|------|----------|
| H1 | 说清项目 | 必过 | 读完「这是什么」能回答：做什么、给谁用、用什么写的、现在什么状态 |
| H2 | 链路能复述 | 必过 | 看「它怎么运转」的图和那段话，能说出输入从哪来、经过哪几步、结果去哪；不能只是 Controller → Service → DB |
| H3 | 知道改哪 | 必过 | 「要改 X 去哪」至少 3 行是这个项目真会改的事，每行指到具体文件或目录 |
| H4 | 能跑起来 | 必过 | 「怎么跑起来」是真实命令，找不到写「未发现」，不写「配置数据库」这类空话 |
| H5 | 风险是项目特有的 | 必过 | 「动手前要知道的」至少 1 条是这个项目特有的，不只是「默认密码 / 弱 JWT」样板 |
| H6 | 诚实边界 | 必过 | 「这份地图没看的」至少 1 条，和【13】、【0】的「未深入」一致 |
| H7 | 不东拼西凑 | 必过 | 导读读起来连贯，同一件事不讲两遍；不贴行号、不打【已核实】（V13/V14 无 WARN） |
| H8 | 篇幅 | 建议 | 约 100 行，不超过 150 行 |

**导读总评**：H1–H7 全过 → 达标；H3 或 H4 是空话 → 不达标。

---

## 二、给 Agent / impact 用的检查（「少盲扫 + 风格可控」测试）

测试方法：模拟 impact Phase 2——只读地图 + `_style-rules.md`（若有），不扫全仓，能否定位变更入口并保持风格。

### 2.1 L1 导航（impact Phase 2 预读）

| # | 检查项 | 级别 | 通过标准 |
|---|--------|------|----------|
| A1 | 模块边界可切片 | 必过 | 【3】覆盖本次变更可能涉及的顶层模块；相关性 3 的有职责描述 |
| A2 | 入口可定位 | 必过 | 【5】HTTP/CLI/定时任务入口表完整；API 前缀明确 |
| A3 | 构建测试可引用 | 必过 | 【8】命令可直接填进 context-pack，非占位 |
| A4 | 权限变更有起点 | 有 auth 则必过 | 【10】机制类型 + 强制点 + 认证-鉴权字段交叉检查（有读源码比对，不是填表） |
| A5 | 风险不进实施建议 | 必过 | 【9】只记录不给修复建议；凭证已脱敏 |
| A6 | 可信度标注可直接用 | 必过 | impact 可把【推断】整段当未确认；HEAD/commit 在【0】可做过期检测 |
| A7 | 调用链可 follow | 建议 | 【4A】evidence 列有一条逐跳调用链，每跳有 file:line 或【推断】 |
| A7A | 核心能力可切片 | 必过 | 【4A】每个阶段有 stage_id、入口、输入/输出、持久化、测试、失败状态和证据/未发现标记 |

**Agent 导航总评**：A1–A3、A5–A6 全过，且有 auth 时 A4 过 → 达标；缺【5】或【8】→ impact 仍要全仓扫 → 不达标。

### 2.2 风格可控（impact Phase 2/3 风格链）

| # | 检查项 | 级别 | 通过标准 |
|---|--------|------|----------|
| A8 | 【14】存在且非空壳 | 必过 | V7 通过；观察表有实质内容（≥2 条非标题行）。自动检查只查"非空壳"，"≥5 轴有内容"是人审标准不是自动检查 |
| A9 | 【14】只描述不规定 | 必过 | 无「必须/禁止/应该统一为」；是「Controller 返回 X」而非「应返回 X」 |
| A10 | 采样来源声明 | 必过 | 写清样本文件、覆盖模块、未覆盖模块（impact 据此降级【14】权重） |
| A11 | 【14】与【13】一致 | 建议 | 未采样模块在【13】或【14】未覆盖里对齐，不能悄悄漏掉 |
| A12 | 与 `_style-rules.md` 分工清晰 | 建议 | 地图不写规范性规则；`_style-rules.md` 存在时 impact 优先级更高（地图不冲突） |

**Agent 风格总评**：A8–A10 全过 → 可控迭代基础具备；只有 V7 标题无表内容 → 空壳，不算达标。

### 2.3 impact 接手模拟（一条变更走通）

用下面 3 问做桌面推演（换真实需求词即可）：

| 推演问题 | 地图应能回答 |
|----------|-------------|
| S1：「改用户手机号字段」从哪进？ | 【3】【5】【6】指向 user 相关路由/model |
| S2：「改登录鉴权」会碰哪些文件？ | 【10】【4A】+【9】已知 defect |
| S3：「新接口返回格式」跟现有一致吗？ | 【14】api_response 轴 + 可选 `_style-rules.md` |

三条都能从地图指到具体路径/风格 → Agent 检查达标；只能答 S1 → 基本达标；都要重新 grep 全仓 → 不达标。

## 三、自动检查（Script Gate，必须通过）

| 检查 | 不过则 |
|------|--------|
| V1 行号真实 | 不可信，impact 不应引用 |
| V2 凭证脱敏 | 红线，禁止归档 |
| V3 SVG 安全 | SVG 已从模板移除，残留即 FAIL |
| V4 【13】非空 | 假装全覆盖（已修复：只匹配 `##` 标题行，不误匹配导航行） |
| V5 Mermaid 一致性 | 实线箭头源节点须在正文出现 |
| V6 facts 与磁盘一致 | 体量/目录造假 |
| V7 【14】存在且有内容 | 风格链断裂（已增强：空壳标题也 FAIL；【13】以超大仓/预算耗尽声明跳过且理由成立时降为 WARN） |
| V8 证据路径格式正常 | 混合路径可能让 V1 basename 回退误判 |
| V9 头部 commit 与 git.json 一致 | 地图与 facts 不同源，过期检测失效 |
| V10 可信度标签密度 + 无修复建议词 | 标签不足 FAIL；疑似修复建议词 WARN |
| V11 facts/地图 HEAD 与当前仓库一致 | 地图过期，须重跑 facts 后刷新 |
| V12 【4A】核心能力链路结构完整 | 缺阶段表、稳定 ID 或机器字段则不可交付 |
| V13 导读七问齐全 | 缺小节、缺运转图或改动导航表 FAIL；超 150 行、贴证据 WARN |
| V14 证据不重复 | 同一条 文件:行号 出现多次 WARN，说明在东拼西凑 |

```bash
python skills/pathfinder/scripts/pf_validate.py \
  change-impact/_project-map.md --repo-root <project-root>
# 期望：SUMMARY: 14 passed, 0 failed, 0 warnings
```

> **注意**：V7 只查「节存在 + 非空壳」，不查【14】内容质量 → A8–A10 必须人工或 L2 评审。

## 四、红线条款（任一即「不可交付」）

- 把【推断】写成【已核实】
- 凭证/密码明文进地图（含风险节）
- 父仓库 HEAD 冒充子项目 commit
- 缺【13】却暗示「已全项目覆盖」
- 【14】写「必须/禁止」当规范（越界成 RuleBlade/impact 的事）
- Script Gate exit ≠ 0 仍交付

## 五、快速打分卡（评审时用）

| 维度 | 权重 | 问一句 |
|------|------|--------|
| 导读 | 40% | 只读导读，同事能否说清项目、知道改哪、怎么跑、要注意什么？ |
| Agent 导航 | 30% | impact 能否跳过全仓扫、直接切到变更模块？ |
| Agent 风格 | 20% | 【14】+ 采样声明能否约束「新代码像旧代码」？ |
| 自动检查 | 10% | 14/14 PASS？ |

| 总分 | 结论 |
|------|------|
| ≥90% 且无红线 | 可交付，可作 impact L1 |
| 75–89% | 可交付但标注缺口（【13】写清待补） |
| <75% 或触红线 | 返工 |

---

## 六、建议用法

1. **Pathfinder 写完** → 先跑 Script Gate → 再按 §一 + §二 人工 10 分钟 review
2. **impact 第一次读地图** → 用 §2.3 推演验证 L1 是否够用；不够就「再挖 X」
3. **跑几次 impact 后** → 把确认的 style 规则追加写入 `_style-rules.md`，地图【14】只作观察补充
