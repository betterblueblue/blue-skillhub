# Intent-Design

## 目标

读取 `INTENT.md` 和 `PRD`，产出两份文档：
- `architecture.md`：全局架构层——分层、模块边界、技术选型、数据流、额外结构与假设。
- `design.md`：功能设计层——每个保留能力在架构里怎么落地。

本 skill 只负责把技术方案外化为文件：

- 不做需求澄清（那是 intent-anchor 的事）。
- 不写 PRD（那是 intent-prd 的事）。
- 不拆工单（那是 intent-issues 的事）。
- 不写代码（那是 intent-dev 的事）。

## 前置条件

1. 必须存在通过 `intent_validate.py` 校验的 `INTENT.md`。没有则停止，提示用户先运行 intent-anchor。
2. 必须存在通过 `prd_validate.py` 校验的 `PRD`。没有则停止，提示用户先运行 intent-prd。

## 轻量档

INTENT.md 第 2 节标注轻量档时：

- 两份文档允许薄写法：架构概览两三句、各表每行一条、能力设计每能力 3-5 行。必需章节和表结构不变，`design_validate.py` 照常运行。
- Phase 1 的路径确认并入草稿确认（草稿开头列出输入文件路径）。
- 设计过程中发现需要数据库/权限/对外 API 时，触发升档单向规则：停下来告知用户升为标准档。

## 工作流程

### Phase 1：前置检查

1. 确认 INTENT.md 和 PRD 路径。路径不明时询问用户，不自动选择"最新一份"。
2. 读取两者全文。
3. 运行 `intent_validate.py` 和 `prd_validate.py` 确认通过。任一 FAIL 则停止。
4. 从 INTENT.md 路径推导链路目录（INTENT.md 的父目录），两份文档写入同一目录下的 `architecture.md` 和 `design.md`。不创建目录、不写文件。

输出：确认后的 INTENT.md 路径、PRD 路径和候选产物路径。

### Phase 2：生成架构文档

1. 探索代码库（如果目标项目已有代码），了解现状。
2. 按 `templates/architecture.md` 的骨架生成草稿：
   - **架构概览**：一段话说清整体思路和分层。不画图，不列目录树。
   - **模块与边界**：每个模块一行，标明职责、服务的能力 ID（INTENT.md 第 4 节保留能力）、依赖模块（只能填本表已定义的模块名）。
   - **技术选型**：每个决策一行。「为什么不选另一个」必须写具体对比理由，不许写"更成熟""更稳定""最佳实践"这类没有对照的说法。「以后再改的成本」只填"便宜"或"贵"。
   - **关键数据流**：INTENT.md 第 14 节的每条验收路径都要有一行。「经过模块」只能填第 2 节已定义的模块名。
   - **额外结构与假设**：凡是用户没有明确要求、为了应对某种情况而多加的结构（新增抽象层、并发控制、缓存、事件机制、额外状态字段、配置项、独立表或服务），逐条列出。必须写出：
     - 为了解决什么具体情况（不许写"为了扩展性""为了健壮性"）
     - 这种情况的依据（只能是代码位置、用户原话、"无依据，属于假设"三种）
     - 以后再改的成本（便宜/贵）
   - 「需要你确认的假设」：把上面标了"无依据"的逐条列出并提问。一次问完，不要边问边继续设计。没有时写"无"。
   - **关键选型与代价（请重点核对）**：只给第 3 节和第 5 节中成本填"贵"的条目写说明，每条按三要素分行（选了什么/依据/做错的代价）。成本填"便宜"的条目不要在这里出现。
3. 如果探索代码库时发现了与 INTENT.md 或 PRD 冲突的信息，停下来告诉用户，不要自行改写原意。

输出：完整 architecture.md 草稿。

### Phase 3：生成功能设计文档

1. 按 `templates/design.md` 的骨架生成草稿：
   - **设计概览**：说明覆盖哪些能力，共几项。
   - **能力设计**：每个保留能力一节，标题格式 `### [C01] {能力名}`。每节写：
     - 涉及模块（引用 architecture.md 第 2 节已定义的模块名）
     - 数据流转（数据怎么进来、怎么变、怎么出去）
     - 关键状态变化（有状态机的写状态迁移，没有写"无"）
     - 数据→展示契约（涉及界面/字段的能力必填：后端存储的机器值（状态/枚举/字典）→ 界面文案映射；图片/文件字段写上传与展示方案；没有则写"无"）
     - 不做什么（必填，写清本次明确不覆盖的部分）
   - **与架构文档的对照**：核对有没有偏离 architecture.md。新增模块必须显式列出或写"无"。
2. 不写接口签名、字段类型、目录结构——那些属于实现。

输出：完整 design.md 草稿。

### Phase 4：确认并写入

1. 在回复中展示两份草稿。
2. 用户确认全文后，将两份文档写入链路目录下的 `architecture.md` 和 `design.md`。
3. 运行：

   ```bash
   python "{intent-design skill 目录}/scripts/design_validate.py" "{architecture 路径}" "{design 路径}" "{intent.md 路径}"
   ```

4. 修复结构问题后重新运行。若修复改变了能力覆盖或模块引用，之前的全文确认立即失效，必须重新确认。

输出：通过结构校验的 architecture.md 和 design.md。

### Phase 5：完成

`architecture.md` 和 `design.md` 已写入 `intent-chain/{链路目录}/`。下一步：运行 intent-issues，输入 intent.md、prd.md 和本次产出的 architecture.md、design.md。

## 强制规则

1. **INTENT.md 和 PRD 必须存在且通过校验**：不通过则不生成设计文档。
2. **每个保留能力必须在功能设计中有一节**：不得遗漏。
3. **每条验收路径必须出现在关键数据流中**：不得跳过。
4. **额外结构必须写出具体场景和依据**：不许写"为了扩展性"这类抽象理由；依据只能是代码位置、用户原话或"无依据，属于假设"。
5. **不写接口签名、字段类型、目录结构**：那些属于实现。
6. **先确认再写文件**：在对话中展示完整草稿，得到明确确认后才写入。用户回复“确认”即构成全文确认；“继续”“嗯”“可以”不算。
7. **结构校验必须通过**：写入后运行 `design_validate.py`（需传入 architecture.md、design.md 和 intent.md 三个路径），校验器会交叉检查模块引用、能力覆盖、假设合规性。
8. **上游已答不重问**：用户已在 INTENT.md 或上游链路文档中明确记录的信息（技术偏好、无性能/安全要求、术语表等），直接引用记录使用，不再重复提问；仅当发现现状与记录冲突时才向用户确认。
9. **按模板写入**：写入 architecture.md 和 design.md 前必须先读取 `templates/architecture.md` 和 `templates/design.md`，按模板的章节结构和行格式产出。本文件的「必需章节」清单只是概要，模板才是完整格式契约。
10. **对用户说人话**：面向用户的汇报、提问和确认请求中，链路内部分类词（如 AFK/HITL）首次出现必须括注一句解释；INTENT.md 术语表已收录的词，对用户表述时使用"人话翻译"或"界面文案"侧，不用原始术语（用户自己先用了原词的除外）。确认请求必须让用户看得懂再确认。括注解释过的领域词若尚未收录进术语表，主动提请登记（anchor 阶段直接补入第 13 节；下游阶段提醒用户回 intent-anchor 补登记后重跑校验）——需要解释的词就是黑话，解释行为本身即登记信号。
11. **展示契约必填**：每个能力的功能设计必须写明「数据→展示契约」——凡有状态/枚举/字典/下拉/图片/文件字段，必须写清机器值到界面文案的映射及上传展示方案；没有则写"无"。

## architecture.md 必需章节

1. 架构概览
2. 模块与边界
3. 技术选型
4. 关键数据流
5. 额外结构与假设
   - 需要你确认的假设
6. 关键选型与代价（请重点核对）

## design.md 必需章节

1. 设计概览
2. 能力设计（每个保留能力一节）
3. 与架构文档的对照

## 文件存放

最终文件放在目标项目根目录：

```text
intent-chain/{链路目录}/architecture.md
intent-chain/{链路目录}/design.md
```

- 链路目录由 intent-anchor 创建，两份文档写入同一目录。
- 同一产品的修订覆盖原文件。

## 能力边界

Intent-Design 能够：

- 从 INTENT.md 和 PRD 原生推导架构和功能设计。
- 用假设表把"这个场景会不会发生"从模型的隐含判断变成用户的显式决策。
- 通过校验器检查模块引用、能力覆盖、假设合规性。

Intent-Design 做不到：

- 自动判断技术方案是否合理。
- 代替用户确认设计文档。
- 防止直接对话场景下的过度设计（那是律刃的事）。
