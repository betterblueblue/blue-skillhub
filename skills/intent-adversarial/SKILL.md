# Intent-Adversarial

> **脚本路径**：本技能目录是 `${CLAUDE_SKILL_DIR}`，命令里的 `{intent-adversarial skill 目录}` 指的就是它；`templates/`、`scripts/` 在它下面，`../_common` 和其他 intent-* 技能在它旁边。这个路径没被替换成实际目录时（别的客户端），用本 SKILL.md 所在目录的绝对路径。

## 写入边界

- 写入：`FIX-*` 缺陷工单（`defects.md`）与对抗验证记录（`adversarial-record.md`）。
- 攻击、灌数据和压测只打用户确认过的非生产目标（见 Phase 1）；不写无关文件。

## 目标

把系统当敌人打。intent-dev 验证「正常用户能用的功能对」、intent-verify 验证「用户路径走得通」，本 skill 验证「**恶意输入和高并发打不穿**」：

- **安全攻击实测**：INTENT 第 16 节每条 SF 要求都用攻击用例实测，不满足于"代码里有校验"的静态确认——本轮实战证明静态确认对注册提权、缺失归属校验零命中。
- **并发一致性断言**：INTENT 第 15 节每条 CC 要求逐条攻击实测（如「库存=1 时 N 并发支付，成功 ≤ 1」）——超卖、重复抢单这类缺陷串行测试永远抓不到。
- **性能基线**：数据放大到真实规模后再测，空库压测无意义。

本 skill 只做对抗性验证与缺陷工单生成：

- 不修复代码（缺陷生成 FIX-* 工单，由 intent-dev 承接修复，回到本 skill 定向复验）。
- 不做路径级功能验收（那是 intent-verify 的事）。

## 前置条件

1. INTENT.md、issues.md、dev-record.md、architecture.md 存在且通过各自校验器。
2. dev-record 中所有工单标 done。
3. 系统可在本机或测试环境运行，且目标环境已经用户确认（见 Phase 1 第 3 步）。

## 轻量档

INTENT.md 第 2 节标注轻量档时，流程不变：SF/CC 逐条实测、真实并发执行都不降级。轻量档项目通常没有登录、角色和对外接口，对应的攻击类别按下文「不适用」规则记录，不为凑齐六类编造用例。

## 攻击用例模板（六类，逐类处理）

测试身份按 INTENT.md 和 architecture.md 里的角色与权限构造：每个角色至少一个账号；要测横向越权的角色，准备两个同角色账号（A / B）。下面括号里的电商例子只是示例，按本项目的接口和资源替换。

1. **垂直越权**：低权限账号逐个调用高权限接口，预期全部 401/403。（例：普通用户调押金终审、人工退款、账号管理）
2. **横向越权**：账号 A 逐个操作账号 B 的按 id 资源，预期全部拒绝或静默无效果，调完查库确认数据没变。（例：订单详情、地址增删改、收藏删除）
3. **跨角色越权**：角色 X 操作只属于角色 Y 的资源，预期拒绝。（例：门店操作他店订单）
4. **未授权访问**：不带凭证访问全部非公开接口，预期 401。
5. **业务逻辑攻击**：冒用他人凭据、重复提交、对已取消的单据继续操作、负数或超大参数、并发抢同一资源。（例：冒用他人优惠券、重复支付同一单）
6. **暴力破解与滥用**：连续登录失败是否触发锁定、注册时能否提权。

**不适用**：项目里没有某一类的攻击面时（例如单用户 CLI 没有登录、角色和对外接口），该类在记录里写一行「不适用」，并写明依据（引用 INTENT.md 第 2 节档位，或 architecture.md 中说明没有该攻击面的内容）。有攻击面的类别必须实测。

## 性能压测三步法

INTENT.md 第 15 节没有 PF 要求时，不做压测，性能基准节写「无性能要求，不适用」。有 PF 要求时：

1. **数据放大**：按 INTENT 性能要求推导规模（如并发 1000 → 万级业务行），批量灌入放大数据。
2. **基准采集**：核心接口串行 N 次，记录 avg / p50 / p95。
3. **并发压测**：每接口 200 请求 / 20 并发（PF 要求更高时按要求调整），记录 rps / p95 / 5xx 数；同时执行 CC 类一致性断言。

## 工作流程

### Phase 1：前置检查
1. 确认 INTENT.md、issues.md、dev-record.md、architecture.md 存在且通过校验。
2. 从 INTENT 第 16 节提取全部 SF 编号、第 15 节提取全部 CC 编号——本 skill 的验证清单。对照六类模板，逐类判断本项目有没有对应的攻击面。
3. **确认目标环境**：向用户列出要攻击和灌数据的目标（服务地址、数据库或库名），说明会产生的副作用（账号被锁、批量写入测试数据、越权写尝试）和清理方式。用户回复「确认」后才进入 Phase 2。目标是生产环境、或说不清是不是生产环境时，停止。目标和用户确认原话记入 adversarial-record 第 1 节。
4. **验收数据准备**：灌入种子数据并按 PF 要求放大；确认清理方式（跑完后恢复干净演示态）。

### Phase 2：安全攻击实测
按六类模板生成用例并逐个执行；没有攻击面的类别按「不适用」规则记录。每条 SF 要求至少被一类中的用例覆盖；每个用例记录：请求、响应、DB 副作用核查结果。

### Phase 3：性能压测与并发一致性
有 PF 要求时按三步法执行。CC 类每条断言构造并发场景实测，记录成功数与最终数据状态。

### Phase 4：缺陷工单生成
发现的每个漏洞/未达标项生成缺陷工单：
- 编号 `FIX-序号`，Phase 5 用户确认后写入链路目录 `defects.md`
- 内容：严重度（高/中/低）、复现步骤、证据（请求/响应/DB 状态）、归属建议
- **严重度为高的缺陷未全部修复 → adversarial-record 结论不得通过，链级校验 FAIL**
- 修复完成后（intent-dev 承接 FIX-* 工单），回到本 skill **定向复验**：只重跑与缺陷相关的用例，全绿才关闭。状态改为 `fixed(复验证据)` 或 `已修复（复验证据）`；校验器只认以 fixed / 已修复 开头的状态

### Phase 5：确认并写记录
1. 先读取 `templates/adversarial-record.md`，按模板的章节和表格写草稿。
2. 在对话中展示完整的记录草稿和缺陷清单，用户回复「确认」后，写入 `intent-chain/{链路目录}/adversarial-record.md`（有缺陷时同时写 `defects.md`）。什么算确认见 `../_common/rules.md`「确认语义」。
3. 运行：

   ```bash
   python "{intent-adversarial skill 目录}/scripts/adversarial_validate.py" "{adversarial-record 路径}" "{intent.md 路径}"
   ```

4. 随后运行 `../_common/chain_validate.py`（传入链路目录）确认链路状态，交接给 intent-verify 做端到端验收。

## 强制规则

1. 六类安全攻击用例逐类处理，不得只挑几类：有攻击面的必须实测，没有攻击面的写「不适用」并附依据。
2. INTENT 的每条 SF 和 CC 必须有对应的攻击实测记录，缺一条 → FAIL。
3. **并发一致性断言必须真实并发执行**（Promise.all / 线程池），串行调用不算。
4. 高危缺陷未修复不得通过；缺陷清单必须在 adversarial-record 中逐条列出。
5. 攻击实测产生的一切数据变更，跑完必须恢复干净演示态。
6. 静态代码确认（"代码里有校验"）不构成通过证据。
7. **只打确认过的非生产目标**：Phase 1 第 3 步没有得到用户确认，不发任何攻击请求、不灌数据、不压测。
8. **先确认再写文件**：记录草稿给用户看过并得到「确认」后才写入。
9. **对用户说人话**：面向用户的汇报、提问和确认请求，按 `../_common/rules.md`「面向用户表述」执行。

## adversarial-record.md 必需章节

1. 验证概述（产品名、输入路径、目标环境与用户确认原话、SF/CC 清单规模、数据放大规模）
2. 数据准备（种子来源、放大规模、清理方式）
3. 安全攻击结果（六类用例表：类别 / 用例 / 关联 SF / 结果 / DB 核查；不适用的类别写一行并附依据）
4. 并发一致性结果（CC 逐条：断言 / 并发场景 / 实测结果 / 通过与否）
5. 性能基准（接口 / avg / p50 / p95 / rps / 5xx）
6. 缺陷清单（FIX-* / 严重度 / 描述 / 状态：open→fixed）
7. 结论（通过 / 不通过；不通过时列出阻断缺陷）

## 能力边界

能够：攻击实测、并发一致性断言、性能基线、缺陷工单生成与定向复验。
不能：修复代码（生成 FIX-* 工单交 intent-dev）、替代 intent-verify 的路径验收与漂移复核。
