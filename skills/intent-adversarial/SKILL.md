# Intent-Adversarial

## 写入边界

- 写入：`FIX-*` 缺陷工单与对抗验证记录（`adversarial-record`）。
- 安全攻击实测仅限被测系统；不写无关文件。

## 目标

把系统当敌人打。intent-dev 验证「正常用户能用的功能对」、intent-verify 验证「用户路径走得通」，本 skill 验证「**恶意输入和高并发打不穿**」：

- **安全攻击实测**：INTENT 第 16 节每条 SF 要求都用攻击用例实测，不满足于"代码里有校验"的静态确认——本轮实战证明静态确认对注册提权、缺失归属校验零命中。
- **并发一致性断言**：INTENT 第 15 节每条 CC 要求逐条攻击实测（如「库存=1 时 N 并发支付，成功 ≤ 1」）——超卖、重复抢单这类缺陷串行测试永远抓不到。
- **性能基线**：数据放大到真实规模后再测，空库压测无意义。

本 skill 只做对抗性验证与缺陷工单生成：

- 不修复代码（缺陷生成 FIX-* 工单，由 intent-dev 承接修复，回到本 skill 定向复验）。
- 不做路径级功能验收（那是 intent-verify 的事）。

## 前置条件

1. INTENT.md、issues.md、dev-record.md、architecture.md 存在且通过各自校验器。
2. dev-record 中所有工单标 done。
3. 系统可在本机或测试环境运行。

## 攻击用例模板（六类，安全攻击实测必须覆盖全部六类）

以双身份（用户 A / 用户 B）+ 管理员 + 门店 + 摄影师 token 为测试身份：

1. **垂直越权**：低权限 token 逐个调用管理接口（押金终审、人工退款、提现打款、账号管理），预期全部 401/403。
2. **横向越权**：用户 A 的 token 逐个操作用户 B 的按 id 资源（订单详情/取消/退款/改期、地址增删改、收藏删除、售后补充凭证、消息已读），预期全部拒绝或静默无效果（调后查库确认数据未变）。
3. **跨角色越权**：门店操作他店订单/押金、摄影师交付他人订单，预期拒绝。
4. **未授权访问**：无 token 访问全部非公开接口，预期 401。
5. **业务逻辑攻击**：冒用他人优惠券、重复支付同一单、支付已取消订单、负数/超大参数污染、并发库存（N 并发抢 M 件）、并发抢单同一单、重复终审。
6. **暴力破解与滥用**：连续登录失败触发锁定、开放注册提权测试。

## 性能压测三步法

1. **数据放大**：按 INTENT 性能要求推导规模（如并发 1000 → 万级业务行），批量灌入放大数据。
2. **基准采集**：核心接口串行 N 次，记录 avg / p50 / p95。
3. **并发压测**：每接口 200 请求 / 20 并发，记录 rps / p95 / 5xx 数；同时执行 CC 类一致性断言。

## 工作流程

### Phase 1：前置检查
1. 确认 INTENT.md、issues.md、dev-record.md、architecture.md 存在且通过校验。
2. 从 INTENT 第 16 节提取全部 SF 编号、第 15 节提取全部 CC 编号——本 skill 的验证清单。
3. **验收数据准备**：灌入种子数据并按 PF 要求放大；确认清理方式（跑完后恢复干净演示态）。

### Phase 2：安全攻击实测
按六类模板生成用例并逐个执行。每条 SF 要求至少被一类中的用例覆盖；每个用例记录：请求、响应、DB 副作用核查结果。

### Phase 3：性能压测与并发一致性
按三步法执行。CC 类每条断言构造并发场景实测，记录成功数与最终数据状态。

### Phase 4：缺陷工单生成
发现的每个漏洞/未达标项生成缺陷工单：
- 编号 `FIX-序号`，写入链路目录 `defects.md`
- 内容：严重度（高/中/低）、复现步骤、证据（请求/响应/DB 状态）、归属建议
- **严重度为高的缺陷未全部修复 → adversarial-record 结论不得通过，链级校验 FAIL**
- 修复完成后（intent-dev 承接 FIX-* 工单），回到本 skill **定向复验**：只重跑与缺陷相关的用例，全绿才关闭

### Phase 5：写记录
结果写入 `intent-chain/{链路目录}/adversarial-record.md`，运行 `adversarial_validate.py` 确认结构通过。随后运行 `chain_validate.py` 确认链路状态，交接给 intent-verify 做端到端验收。

## 强制规则

1. 六类安全攻击用例必须全部覆盖，不得只挑几类。
2. INTENT 的每条 SF 和 CC 必须有对应的攻击实测记录，缺一条 → FAIL。
3. **并发一致性断言必须真实并发执行**（Promise.all / 线程池），串行调用不算。
4. 高危缺陷未修复不得通过；缺陷清单必须在 adversarial-record 中逐条列出。
5. 攻击实测产生的一切数据变更，跑完必须恢复干净演示态。
6. 静态代码确认（"代码里有校验"）不构成通过证据。

## adversarial-record.md 必需章节

1. 验证概述（产品名、输入路径、SF/CC 清单规模、数据放大规模）
2. 数据准备（种子来源、放大规模、清理方式）
3. 安全攻击结果（六类用例表：类别 / 用例 / 关联 SF / 结果 / DB 核查）
4. 并发一致性结果（CC 逐条：断言 / 并发场景 / 实测结果 / 通过与否）
5. 性能基准（接口 / avg / p50 / p95 / rps / 5xx）
6. 缺陷清单（FIX-* / 严重度 / 描述 / 状态：open→fixed）
7. 结论（通过 / 不通过；不通过时列出阻断缺陷）

## 能力边界

能够：攻击实测、并发一致性断言、性能基线、缺陷工单生成与定向复验。
不能：修复代码（生成 FIX-* 工单交 intent-dev）、替代 intent-verify 的路径验收与漂移复核。
