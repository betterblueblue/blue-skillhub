# Intent-Verify

## 目标

所有工单开发完成后，做整体验收。先跑全量测试确认老功能没被改坏，再按 INTENT.md 第 14 节的验收路径逐条端到端走通，确认用户可感知的路径全部能用。核对保留能力是否都有实现或验证证据，检查有没有偷偷丢掉或加上什么。如果 INTENT.md 有性能或安全要求，按要求验证。

打个比方：intent-dev 检查的是每个零件合不合格，intent-verify 做的是把零件装成整机，通电试跑。

本 skill 只负责端到端验收和阶段门禁：

- 不开发代码（那是 intent-dev 的事）。
- 不做需求澄清（那是 intent-anchor 的事）。
- 不写 PRD（那是 intent-prd 的事）。
- 不拆工单（那是 intent-issues 的事）。
- 不重新验工单的验收标准（那是 intent-dev 已经做过的）。

## 前置条件

1. 必须存在通过 `intent_validate.py` 校验的 `INTENT.md`。
2. 必须存在通过 `prd_validate.py` 校验的 `PRD`。
3. 必须存在通过 `issues_validate.py` 校验的工单文件。
4. 必须存在通过 `dev_validate.py` 校验的 `dev-record.md`。
5. 必须存在通过 `design_validate.py` 校验的 `architecture.md` 和 `design.md`。
6. 六个前置文件缺一不可，且 dev-record 中所有工单必须标 done。

## 验证等级

端到端验收使用 V3 等级：

| 等级 | 含义 | 证据要求 |
|---|---|---|
| V3 | 端到端验证通过 | 验收路径实际走通的证据 |

**铁律：标 V3 但没有实际走通的证据 → 不通过。**

## 工作流程

### Phase 1：前置检查

1. 确认 INTENT.md、PRD、工单文件、dev-record、`architecture.md` 和 `design.md` 路径。
2. 读取全部文件。
3. 确认 `architecture.md` 和 `design.md` 存在，运行 `design_validate.py` 确认通过。缺失或 FAIL 则停止，提示用户先运行 intent-design。
4. 运行 `intent_validate.py`、`prd_validate.py`、`issues_validate.py` 和 `dev_validate.py` 确认通过。任一 FAIL 则停止。
5. 确认 dev-record 中所有工单标 done。有未完成工单则停止。
6. 从输入文件路径推导链路目录，VERIFY-RECORD 写入同一目录下的 `verify-record.md`。不创建目录、不写文件。
7. 如果 verify-record 已存在（跨会话恢复），读取现有记录，复述当前进度。

输出：确认后的文件路径、验收路径清单和当前进度。

### Phase 2：回归验证

**验证依据：项目的全量测试。** 目的是确认工单改动没有把老功能改坏。

1. 运行项目的全量测试命令（如 `npm test`、`mvn test`、`go test ./...`）。
2. 捕获完整输出。
3. 全部通过 → 记录命令和输出摘要。
4. 有失败 → 记录失败项和原因，标为"回归未通过"。
5. 项目没有测试命令 → 标"无全量测试，回归验证不适用"。

如果有集成测试命令（如 `npm run test:integration`），也运行并记录结果。

输出：回归验证结果（通过/未通过/不适用 + 证据）。

### Phase 3：端到端验收

**验证依据：INTENT.md 第 14 节的验收路径。** 不是重新验工单的验收标准，而是验整条用户路径是否走通。

对每条验收路径：

1. **Given（前置条件）是否就绪**：确认路径开始前需要的条件是否满足。比如"用户已登录"、"数据库有测试数据"等。
2. **When（触发操作）是否执行**：实际执行路径中的操作。比如打开页面、点击按钮、调用接口。
3. **Then（预期结果）是否达成**：确认每条预期结果。比如看到正确的内容、数据存进了数据库、文件生成在正确位置。
4. **验证方式**（按优先级）：
   - 第一优先级：运行项目已有的 E2E 测试命令。
   - 第二优先级：启动项目后手动走路径（启动服务 → 操作 → 看结果）。适合人在旁边时人工走查。
   - 第三优先级：浏览器自动化（Playwright）。AI 在对话环境中没有手，"手动走路径"需要通过 Playwright 才能真正执行——启动服务后用 Playwright 打开页面、点击、填表、跳转、断言 DOM 和截图。curl/fetch 只能验 API 返回，验不了页面渲染和前端交互。
   - 第四优先级：运行 API 脚本验证接口行为（curl / fetch / httpie）——但 API 结果只能作为 UI 验证的补充证据，不能单独构成 V3。
   - 都不行 → 标"无法验证"，提示用户。
5. **每条路径必须有 V3 证据**——实际走通的结果，不能只写"应该没问题"。
6. **有设计标准时（INTENT 第 12 节有素材），路径证据必须写 `截图：{相对链路目录的路径}` 或 `Playwright 产物：{路径}`，且文件必须真实存在**；只写「浏览器」「前端已渲染」不算。

输出：每条路径的 V3 验证结果。

### Phase 3.5：页面走查（INTENT 第 17 节有页面清单时必做）

路径验收验主流程，页面走查补页面级缺陷（本轮实战：竞态崩溃、Tab 筛选失效均只有真点页面才暴露）。

1. **验收数据准备**：按 INTENT 场景灌入种子/真实规模数据，并约定清理方式（验收后恢复干净演示态）。走查是污染性操作，无数据准备不得开始。
2. 以第 17 节页面清单为清单，**每页至少 1 个真点交互**（Playwright 打开、操作关键控件、断言 DOM/数据），并监听 pageerror——JS 运行时异常必须为零。
3. 每页记录走查结果（通过 / 缺陷），发现的缺陷进入 Phase 4.5 缺陷闭环。
4. 第 17 节缺失时（历史链路）标"无页面清单，页面走查不适用"，但必须提示用户补跑 intent-anchor。

### Phase 4：条件性验证

**验证依据：INTENT.md 中的性能、安全和并发一致性要求。** 有要求才验，没有就跳过。

1. **性能验证（三步法，空库计时不算验证）**：
   - 检查 INTENT 第 15 节 PF 要求。
   - 有要求 → 三步执行：①**数据放大**（按 PF 推导规模批量灌数据，如并发 1000 → 万级业务行）；②**基准采集**（核心接口串行 N 次记录 avg/p50/p95）；③**并发压测**（200 请求/20 并发，记录 rps、p95、5xx）。
   - 对照 PF 阈值逐条判定，记录完整数据。
   - 无要求 → 标"无性能要求，不适用"。
2. **安全验证（攻击实测，静态确认不算）**：
   - 检查 INTENT 第 16 节 SF 要求。
   - 有要求 → 按攻击用例六类模板（垂直/横向/跨角色越权、未授权、业务逻辑攻击、暴力破解）实测，双身份构造。**"代码里有校验"不构成通过证据**——实战证明注册提权、缺失归属校验均通过静态确认漏检。
   - 无要求 → 标"无安全要求，不适用"。
3. **并发一致性验证**：INTENT 第 15 节 CC 类逐条攻击实测（真实并发执行 + DB 断言）。若已运行 intent-adversarial，此处复核 adversarial-record 的结论与缺陷关闭状态即可。
4. 无对应要求时逐项标"不适用"。

输出：条件性验证结果（有要求的逐项验证，无要求的标不适用）。

### Phase 4.5：缺陷闭环

验收（Phase 2-4）发现的每个缺陷：

1. 生成缺陷工单：编号 `FIX-序号`，写入链路目录 `defects.md`（严重度/复现步骤/证据/归属建议）。跨工单的系统性问题（状态机缺口、竞态）也要建单，不因其"不属于任何工单"而搁置。
2. 高危缺陷（安全漏洞/数据一致性/核心路径断裂）**未全部修复前，verify-record 结论不得为通过，不得交付**；一般缺陷可带病交付但必须在最终复核中显式列出。
3. 修复（intent-dev 承接 FIX-* 工单）后**定向复验**：只重跑与缺陷相关的路径、用例和回归测试，全绿才关闭。
4. 全部缺陷关闭后重新汇总 Phase 5，进入收尾。

### Phase 5：最终复核

1. **回归验证结果**：汇总 Phase 2 的结果。
2. **保留能力逐项核对**：按 INTENT.md 第 4 节的保留能力列表，逐项检查是否有实现或验证证据。来源是 dev-record 和 Phase 3 的验证结果。
3. **验收路径逐条验证**：汇总 Phase 3 的结果，每条路径标 V3 和证据。
4. **条件性验证结果**：汇总 Phase 4 的性能和安全验证结果。
5. **漂移复核**：按 INTENT.md 第 7 节的 7 种漂移模式，检查是否有能力被静默降级、遗漏或重新加入。
6. **技术漂移复核**：列出实际代码中的模块划分，与 architecture.md 第 2 节和 design.md 的涉及模块对照。表格四列：模块名 / 在 architecture.md 中 / 状态（一致 / 新增 / 缺失）/ 说明。新增模块必须显式列出（状态标"新增"，说明列写原因）；缺失模块状态标"缺失"并说明原因。标"新增""缺失"的行校验器不做存在性比对——如实报告漂移不会导致校验失败。
7. **设计标准核对**：如果 INTENT.md 第 12 节有设计标准，检查 UI 是否对照设计文件通过；若发现设计标准被推翻或变更（含用户中途改需求），执行强制规则 13 回写重验。
8. 在对话中展示完整的最终复核结果。
9. 用户确认后，将结果写入 verify-record.md。
10. 运行 `verify_validate.py` 确认 verify-record 结构通过（需传入 verify-record.md、intent.md、architecture.md 和 design.md 四个路径）。

输出：通过校验的 verify-record.md。

### Phase 6：完成

`verify-record.md` 已写入 `intent-chain/{链路目录}/`。**交接前必须运行链级校验器 `skills/_common/chain_validate.py`（传入链路目录），全部 PASS 或合法跳过才允许结束；任一 FAIL 不得宣告链路走完。**

**链路走完后，执行体系回流（Skill 自我进化环节，不可跳过）**：

1. 检查 `blue-skillhub/_improvements/verification-cards.md` 是否存在。存在 → 本次会话在推进项目时应已按 VALIDATION-PROMPT.md 执行了各卡验证；把结果按模板写入 `blue-skillhub/_improvements/verifications/{日期}-{项目名}.md`，并更新 STATUS.md 的条目状态与归因分布。
2. 本次会话暴露的 SKILL/校验器自身问题（指引不清、校验器误报漏报、模板缺失），逐条登记进 `_improvements/` 的新 backlog（或追加到已有 backlog），按归因三分类标注。
3. `_improvements` 不存在（如本 skill 被复制到其他仓库独立使用）→ 跳过回流，但在交接内容中提醒用户：这套链路有配套的改进验证体系，位于 blue-skillhub 仓库。

链路走完后，后续如需变更，使用 impact 做影响分析；如需新增功能，从 intent-anchor 重新开始。

## 轻量档

INTENT.md 第 2 节标注轻量档时，本 skill 流程不变——全量回归、逐路径 V3 证据、漂移复核、技术漂移复核一概不降级。轻量档降的是上游文档厚度和确认次数，不是验收强度。

## 强制规则

1. **六个前置文件必须存在且通过校验**：不通过则不进入验收。
2. **dev-record 中所有工单必须标 done**：有未完成工单则停止。
3. **必须跑全量测试**：有测试命令就必须跑，不能跳过。没有测试命令才标不适用。
4. **每条验收路径必须有 V3 证据**：实际走通的结果，不能只写"应该没问题"。
5. **性能/安全要求有则必验**：INTENT.md 或 PRD 中写了性能或安全要求就必须验证，不能跳过。
6. **保留能力必须逐项核对**：不能跳过。
7. **漂移复核必须逐项检查**：7 种模式全部覆盖。
8. **先确认再写文件**：在对话中展示结果草稿，得到确认后才写入。用户回复“确认”即构成确认；“继续”“嗯”“可以”不算。
9. **结构校验必须通过**：写入后运行 `verify_validate.py`（需传入 verify-record.md、intent.md、architecture.md 和 design.md 四个路径），校验器会交叉检查路径 ID、保留能力 ID 和性能/安全结论是否与 INTENT.md 一致，检查技术漂移复核子节是否有数据行且模块名与 architecture.md 和 design.md 一致（状态标"新增""缺失"的行不做存在性比对，改查说明列是否写明原因）。
10. **上游已答不重问**：用户已在 INTENT.md 或上游链路文档中明确记录的信息（技术偏好、无性能/安全要求等），直接引用记录使用，不再重复提问；仅当发现现状与记录冲突时才向用户确认。
11. **按模板写入**：写入 verify-record.md 前必须先读取 `templates/verify-record.md`，按模板的章节结构和行格式产出。本文件的「必需章节」清单只是概要，模板才是完整格式契约。
12. **对用户说人话**：面向用户的汇报、提问和确认请求中，链路内部分类词（如 AFK/HITL）首次出现必须括注一句解释；INTENT.md 术语表已收录的词，对用户表述时使用"人话翻译"或"界面文案"侧，不用原始术语（用户自己先用了原词的除外）。确认请求必须让用户看得懂再确认。括注解释过的领域词若尚未收录进术语表，主动提请登记（anchor 阶段直接补入第 13 节；下游阶段提醒用户回 intent-anchor 补登记后重跑校验）——需要解释的词就是黑话，解释行为本身即登记信号。
13. **发现上游约束被推翻必须回写重验**：验收过程中若发现实现或用户决策推翻了 INTENT.md 已确认的约束（如设计标准、不可妥协项、性能/安全要求），不得直接标注通过；必须停止，回写 INTENT.md 对应章节，重跑 `intent_validate.py`，并视影响程度回跑下游校验后再继续验收。
14. **写操作必须逐动作实测**：对涉及增/改/删的数据管理类能力，端到端验收必须实际走通「新增 → 列表出现 → 编辑 → 删除 → 列表消失」；仅查询、接口返回或测试全绿不算，走不通的写动作不得标 V3。

## verify-record.md 必需章节

1. 验收概述（产品名称、前置文件路径、验收路径总数、dev-record 路径）
2. 回归验证结果
   - 全量测试命令
   - 输出摘要
   - 通过/未通过/不适用
3. 端到端验收结果
   - 每条路径的 Given/When/Then
   - 验证方式
   - V3 证据
   - 通过/未通过
4. 条件性验证结果
   - 性能验证（三步法：数据放大 → 基准采集 → 并发压测；有要求则逐项验证，无要求则标不适用）
   - 安全验证（攻击实测，静态确认不算；有要求则逐项验证，无要求则标不适用）
   - 并发一致性验证（INTENT CC 类逐条实测，或复核 adversarial-record）
4.5 页面走查结果（INTENT 第 17 节有页面清单时必填：每页真点交互 + JS 异常监听结果）
4.6 缺陷清单（FIX-* / 严重度 / 状态；高危缺陷未全部修复 → 结论不得为通过）
5. 最终复核
   - 回归验证结果汇总
   - 保留能力逐项核对
   - 验收路径逐条验证（每条路径 V3 证据）
   - 条件性验证结果汇总
   - 漂移复核
   - 技术漂移复核（模块名 / 在 architecture.md 中 / 状态 / 说明 四列表格）
   - 页面清单逐页核对（INTENT 第 17 节有页面清单时必填）
   - 结论

## 文件存放

最终文件放在目标项目根目录：

```text
intent-chain/{链路目录}/verify-record.md
```

- 链路目录由 intent-anchor 创建，VERIFY-RECORD 写入同一目录。
- 同一产品的修订覆盖原文件。

## 能力边界

Intent-Verify 能够：

- 跑全量测试确认老功能没被改坏。
- 按 INTENT.md 的验收路径逐条端到端验证。
- 以页面清单为清单做页面走查子模式（真点 + JS 异常监听 + 验收数据准备/清理）。
- 按 INTENT.md 的性能（三步法）、安全（攻击实测）和并发一致性要求做条件性验证。
- 核对保留能力是否都有实现或验证证据。
- 检查 7 种漂移模式是否命中。
- 生成缺陷工单（FIX-*）并做定向复验，形成验收缺陷闭环。
- 通过校验器检查 verify-record 的结构完整性，并与 INTENT.md 交叉校验路径 ID、保留能力 ID 和性能/安全结论。

Intent-Verify 做不到：

- 代替用户开发代码或测试（缺陷修复由 intent-dev 承接 FIX-* 工单）。
- 生成需要长期维护的测试套件（验收产出的 Playwright/API 脚本以「验收快照」名义留存链路目录 `snapshots/`，标注可能过期；后续 impact 变更时先跑快照做回归参考）。
- 重新验工单的验收标准（那是 intent-dev 的事）。
- **高危缺陷未修复时放行交付**（分级阻止：高危缺陷未闭环 → verify-record 结论不得为通过，chain_validate FAIL；一般缺陷可带病交付但必须显式列出）。
