## B. 需求锚定层("1:1 还原"在链路内没有抓手)

### - [x] B1 真值逐层压缩且无反向追溯
- **证据**:Excel 92 页 → INTENT 30 能力 → 22 工单 → 11 验收路径,粒度逐层压缩;无任何环节维护「源材料行 → 能力/工单/页面」的反向映射

- **修复落点**:intent-issues SKILL 强制新增产物「真值追溯表」:源材料每一行(页) → 承接它的工单 ID;校验器检查无孤儿行
- 状态:- [ ] 待办

### - [x] B2 页面清单规则未触发执行
- **证据**:intent-anchor SKILL 规则 11:「当用户要求 1:1 还原/全部页面/逐页还原时,必须从源材料逐页提取页面清单写入第 17 节」。本项目用户需求即 1:1 还原(对应 C01),但 INTENT.md **没有第 17 节**
- **影响**:verify 的「页面清单逐页核对」为条件项(第 17 节存在才必填),条件缺失直接跳过,1:1 还原失去唯一抓手
- **修复落点**:见 B3(触发判定下沉校验器);anchor SKILL 规则 11 可补充:触发判定失败时(如用户原话含糊)主动向用户确认是否为页级要求,而非静默跳过
- 状态:- [ ] 待办

### - [x] B3 校验器声称强制却未拦截
- **证据**:anchor SKILL 规则 11 写明「intent_validate 会强制该校验」,但本项目 INTENT 无 17 节仍通过 intent_validate
- **影响**:规则条文与校验器实际行为不一致,这是三层防线(规则/校验器/用户确认)全部漏过的直接原因
- **修复落点**:`_common/intent_validate.py`:当第 2 节场景类型或用户原话命中页级要求触发词(1:1/全部页面/逐页/还原/功能清单来源登记了页级文件)而第 17 节缺失或行数不足时 → FAIL;第 17 节每行要求带源材料引用(sheet/行号/锚点),行数与源材料实际行数不一致 → WARN/FAIL
- **回归验证方式**:用租衣摄影项目重跑 intent-anchor,预期:不产出 17 节则校验 FAIL
- 状态:- [ ] 待办

### - [x] B4 1:1 完整性判定依赖 Agent 自觉

## C. 验证深度层(验"功能对不对",未验"打不打得穿")

### - [x] C1 走查粒度:路径真点 ≠ 页面真点
- **证据**:三端 UI 真点走查(56 项)抓到 `admin/PhotoManage.vue` 门店推荐竞态崩溃、C 端订单 Tab 筛选失效等页面级缺陷,均不在 11 条验收路径主干上
- **修复落点**:intent-verify SKILL 增加走查子模式:以第 17 节页面清单为清单,每页至少 1 个真点交互 + pageerror 监听;依赖 B2/B3 先落地
- 状态:- [ ] 待办

### - [x] C2 走查无验收数据准备/清理约定
- **证据**:走查/压测是污染性操作(下单/核销/改库存),来源项目靠临时 `seed-realworld.js` 重灌兜底,链路无此机制;测试与演示数据互相污染曾导致 17 个集成测试假失败
- **修复落点**:intent-verify Phase 1 增加固定步骤:「验收数据准备(灌入种子/放大数据)」与「验收后清理」;约定验收目录内留存数据脚本
- 状态:- [ ] 待办

### - [x] C3 性能验证手法未定义
- **证据**:PF02「接口响应 ≤ 1 秒」无工具/并发/数据规模规格;空库 + 手动计时几次即可"通过",该结论无意义
- **修复落点**:intent-verify Phase 4 性能验证定义三步法:**数据放大 → 基准采集(串行 p50/p95)→ 并发压测(请求/秒、p95、5xx)**;给出参考实现底稿(来源项目 scripts/perf-test.mjs)
- 状态:- [ ] 待办

### - [x] C4 无数据放大步骤
- **证据**:1000 服装/2000 订单放大后才暴露 `Order.timeline` varchar(191) 超长(订单走完状态机必 500)、后台订单列表无分页(2000 单 p95 1.3s);空库压测全部正常
- **修复落点**:同 C3 三步法第一步;数据规模建议由 INTENT 性能要求推导(如 PF05 并发 1000 → 至万级业务行)
- 状态:- [ ] 待办

### - [x] C5 并发数据一致性是全链路盲区(本轮最贵的发现)
- **证据**:50 并发抢 10 件库存卖出 50 单(库存 -40);5 摄影师并发抢单同一单全部 500。两缺陷不属于性能(快慢)、不属于安全(攻击)、不属于单工单功能——掉在 INTENT 第 15 节(仅性能)、第 16 节(仅安全)的分类缝里,任何环节均无覆盖
- **修复落点**:INTENT 模板第 15 节增加「并发一致性要求」分类(CC 类:超卖=0、单归属唯一、重复支付拒绝、重复终审拒绝);verify/对抗环节增加对应断言用例
- 状态:- [ ] 待办

### - [x] C6 安全验证是"确认型"而非"攻击型"
- **证据**:5 个真实漏洞(注册提权 ADMIN、favorites/cart/message 无归属校验、租期数值污染)全部靠攻击实测发现;按现 SKILL 验证 SF04 的自然动作是"检查代码有 requireAuth"——静态确认对全部 5 个漏洞零命中
- **修复落点**:SF 类要求逐条定义「验证 = 攻击实测」而非「代码确认」;方法见 C7
- 状态:- [ ] 待办

### - [x] C7 攻击方法论未模板化
- **证据**:security-audit.mjs 的 6 类 31 项用例(垂直越权/横向越权/跨角色/未授权/业务逻辑攻击/暴力破解)是从零构建的,链路无此底稿
- **修复落点**:固化为对抗性验证的攻击用例模板(见 `_improvements/README.md` 资产表)
- 状态:- [ ] 待办

## D. 缺陷闭环层(发现之后没有任何机制)

### - [x] D1 verify 只报告不阻止交付
- **证据**:intent-verify SKILL 能力边界原文:「强制用户修复未通过项(只报告结果,不阻止交付)」
- **影响**:高危缺陷(超卖/提权)即使被验出,交付仍可继续
- **修复落点**:改为分级——高危(安全漏洞/数据一致性/核心路径断裂)缺陷未修复 → **阻止交付**(verify-record 不得全 PASS);一般缺陷可带病交付但必须在链级校验结果中显式列出
- 状态:- [ ] 待办

### - [x] D2 验收缺陷无单可归
- **证据**:押金终审不置已完成、并发竞态等跨工单系统性问题,不属于任何工单的验收标准;回 intent-dev 无承接物
- **修复落点**:verify 发现的缺陷自动生成「缺陷工单」(编号 FIX-*,含复现步骤/证据/归属建议),允许 intent-dev 承接
- 状态:- [ ] 待办

### - [x] D3 无"发现→修复→复验→关闭"循环
- **证据**:本项目靠外部 Agent 临时构建"发现即修+回归"流程
- **修复落点**:verify SKILL 增加缺陷闭环规则:缺陷工单修复后,仅重跑与缺陷相关的验收路径与回归测试(定向复验),全绿才可关闭
- 状态:- [ ] 待办

### - [x] D4 验收不沉淀可复跑资产
- **证据**:verify SKILL 明确"不生成永久 E2E 测试套件"——避免维护负担是有意取舍,但代价是验收一次性;后续 impact 变更后 84+56 项断言无法复跑
- **修复落点**:verify 产出的 Playwright/API 验收脚本以「验收快照」名义留存链路目录(标注可能过期),后续变更时先跑旧脚本做回归参考
- 状态:- [ ] 待办
