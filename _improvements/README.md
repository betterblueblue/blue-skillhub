# _improvements · Skill 体系改进 Backlog

本目录存放**从实战项目复盘中识别出的 Skill 体系问题与改进项**。每个做过完整交付的项目,复盘一份 backlog 文件;问题条目化,修完勾选关闭。体系按「实战 → 复盘 → 修复 → 下轮实战验证 → 回流」循环持续进化。

## 轮次管理约定(多轮迭代规则)

1. **条目 ID 带轮次前缀**:`R{轮次}-{编号}`,如 R1-A1(第一轮 A1)。后续轮次新问题的编号独立,不与历史轮次共用编号空间。
2. **同一病根复发**时:不在新 backlog 另立新义条目,而是新建条目并在其中标注「关联: R1-XX(复发/新症状)」;同时 STATUS.md 中对应条目状态改回 **regressed**。
3. **验证卡版本化**:verification-cards.md 顶部维护变更记录;每份验证报告标注「依据卡版本 {日期}」,保证对比有基准。
4. **聚合视图**:`STATUS.md` 是全部改进项状态的单一真值——每轮复盘/验证后更新;其「归因分布趋势」表是判断体系是否在变好的核心信号(校验器缺口占比应逐轮下降;若「Agent 违反」持续高位,说明文字指引路线到顶,重心必须继续向校验器和自动化倾斜)。
5. **SKILL 修复用 git commit 固化**:backlog 修复记录引用 commit hash,使「SKILL 版本 ↔ 验证报告」可双向追溯。
6. **复盘时机**:项目交付后(或链路验证结束后)。验证报告 + 新 backlog 是同一复盘动作的两面:前者记录改进项验证结果,后者登记新问题与回归。

## 验证闭环(2026-08-30 新增)

修复 ≠ 完成,必须经过**下一个真实项目**的实战验证。本目录的三件套构成验证闭环:

1. **verification-cards.md** — 6 张验证任务卡(按链路环节),每张写明:验证时机、步骤、可机械判定的理想态、失败记录格式。
2. **VALIDATION-PROMPT.md** — 下一个项目会话的引导词(复制到会话开头即可),让新会话在推进项目的同时执行验证,失败项强制归因(校验器缺口 / SKILL 指引不够 / Agent 违反指引)。
3. **verifications/** — 验证报告存放处(按 `TEMPLATE.md` 写),失败项按归因回流到 backlog 对应批次。
4. **STATUS.md** — 全部改进项的聚合状态与归因分布趋势(单一真值)。

**归因 → 优化方向映射**:校验器缺口 → 下沉校验器规则(P0);SKILL 指引不够 → 改 SKILL/补底稿(P1);Agent 违反指引 → 下沉校验器(P0,说明指引对该类 Agent 不可靠)。同一张卡连续 2 个项目失败 → 自动升级 P0。

## 使用约定

- 文件命名:`YYYY-MM-DD-<项目标识>-backlog.md`(日期为复盘日期)
- 每个问题条目带:证据(实测发现,非推测)、影响、修复落点(精确到 SKILL 文件/校验器)、状态
- 状态流转:`- [ ]` 待办 → `- [x]` 已修复(修复时在行尾追加实际改动摘要)
- **修复落点里优先级最高的是校验器**(`_common/*.py` 与各 skill 的 `scripts/`):校验器是这套体系里唯一不依赖 Agent 自觉的执行者,关键约束必须从"SKILL 规则条文"下沉到"校验器硬拦"
- 修复完成后,用一个**历史实战项目做回归验证**:重跑对应 skill,确认当时漏掉的问题这次会被拦住
