# 验证引导词(VALIDATION PROMPT)

> **使用方式**:启动下一个真实项目的意图链路会话时,把下方引导线之间的内容完整复制到会话开头(第一次对话的第一条消息之前或之后均可),让该会话在推进项目的同时执行链路改进验证。

---

## 给下一个项目会话的引导词(复制以下全部内容)

本项目除了交付功能,还承担一个**链路验证任务**。你使用的 intent 系列 SKILL 刚完成一轮改进(20 项),本项目的会话需要验证这些改进在真实执行中是否有效。

**执行要求**:

1. 先读 `blue-skillhub/_improvements/verification-cards.md`(验证任务卡,共 6 张)和 `blue-skillhub/_improvements/2026-08-29-intent-chain-rentphoto-backlog.md`(改进背景与 23 个历史缺陷)。
2. 在链路的每个环节完成后,执行对应验证卡的步骤,并记录结果(通过 / 失败+证据)。验证动作不替代该环节的正常产出,只叠加检查。
3. 任何验证失败,按卡内「失败记录」格式登记,**必须归因到三类之一**:校验器缺口 / SKILL 指引不够 / Agent 违反指引。
4. 项目结束后,把全部验证结果按 `blue-skillhub/_improvements/verifications/TEMPLATE.md` 的模板写入 `blue-skillhub/_improvements/verifications/<日期>-<项目名>.md`,并在 `_improvements/README.md` 的表格中登记一行。
5. 验证过程中不要为了"让验证通过"而降低项目本身的交付标准;也不要为了项目进度跳过验证步骤。两者冲突时,停下来问用户。

**当前验证重点**(按 backlog 归因分类的缺口):V16 触发面扩大后的真实命中率(是否对"决策来源登记页级清单"的项目正确触发);V13 追溯表在真实多页项目中的可用性;adversarial 六类攻击用例在真实项目中的覆盖完整度;CC 类断言的构造质量(是否真的做了并发,还是退化成串行)。

---

## 验证结束后

1. 确认验证报告已写入 `verifications/`,每条失败都有归因。
2. 把「校验器缺口」类的失败项,连同复现输入,追加到 `_improvements/` 对应 backlog 的 P0 区(校验器硬拦优先)。
3. 若同一张验证卡连续两个项目失败,在 backlog 中升级该卡对应改进项的优先级,并在卡片顶部标注「连续失败 N 次」。
