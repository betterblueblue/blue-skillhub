# 验证任务卡(Verification Cards)

> 用途:每个改进项在下一个真实项目中如何被验证。按链路环节归组为 6 张卡。
> 使用方式:项目会话按 VALIDATION-PROMPT.md 引导,在对应环节执行本卡步骤,结果按 verifications/ 模板写回。
> 铁律:理想态必须是**可机械判定的事实**(有/没有、数字、文件存在),不写"质量好"这类感觉词。
>
> **版本记录**(验证报告须标注依据的卡版本):
> - 2026-08-30 v1:首批 6 卡,对应 R1 全部 20 项改进。

## 卡 1 · anchor 环节(验证 B2/B3/B4/V16/V17)

**时机**:intent-anchor 运行完成、intent_validate 通过之后。

**步骤**:
1. 检查产出的 INTENT.md:第 17 节是否存在;若源材料是页级清单(如逐页 Excel),行数是否与源材料一致(或至少触发 WARN 且用户知晓)。
2. 检查第 15 节:CC 类(并发一致性)表是否与用户确认过(或显式声明"无并发一致性要求")。
3. 回看 anchor 会话:规则 11 的"逐页确认"动作是否真实发生(用户看到了完整清单并逐页确认)。

**理想态**:intent_validate 全 PASS(含 V16/V17);17 节行数 = 源材料页数;CC 表有用户确认。

**失败记录**:缺 17 节 / 行数不符 / CC 缺确认 → 记录证据(INTENT 片段)+ 归因(SKILL 指引不够 / 校验器缺口 / Agent 违反)。

## 卡 2 · issues 环节(验证 B1/V13)

**时机**:intent-issues 运行完成、issues_validate 通过之后。

**步骤**:
1. INTENT 第 17 节存在时:issues.md 的「覆盖核对」节是否含「真值追溯」子节;每个页面 ID 是否映射到存在的工单;V13 是否 PASS。
2. 人工抽查 3 行映射:工单的验收标准真的覆盖该页的关键行为吗(不是"挂在某工单下"就算,要看内容)。

**理想态**:V13 PASS;抽查 3 行映射内容真实对应。

**失败记录**:V13 FAIL 但 Agent 没修 → 归因;追溯表存在但映射空洞(页挂了工单但工单内容不覆盖该页)→ 说明 V13 的结构校验不够,需要内容级校验 → 记录。

## 卡 3 · dev 环节(验证 A3/D2)

**时机**:intent-dev Phase 3 完成、全部工单 done 之后。

**步骤**:
1. 检查 dev 收尾输出:是否出现「⚠ 工单级完成 ≠ 链路完成」警告,以及"必须依次运行 adversarial/verify"的交接指引。
2. 若链路存在 FIX-* 缺陷工单:检查 dev 是否承接修复(而不是跳过)。

**理想态**:警告出现;FIX 工单被 TDD 修复。

**失败记录**:警告缺失 → SKILL 指引问题;FIX 工单被跳过 → 门禁问题(考虑把 FIX 工单纳入 dev_validate 的 done 检查)。

## 卡 4 · adversarial 环节(验证 C3-C7/E1,本轮核心新增)

**时机**:dev 完成后、verify 之前;chain_validate 应在此刻对"adversarial-record 缺失"FAIL。

**步骤**:
1. 检查数据放大:是否按 INTENT 性能要求推导了规模(万级业务行),不是空库。
2. 检查六类攻击覆盖:垂直/横向/跨角色越权、未授权、业务逻辑攻击、暴力破解,全部有用例和结果;INTENT 每条 SF 被至少一个用例关联(A3)。
3. 检查 CC 逐条断言:INTENT 每条 CC 都有真实并发的实测记录(成功数/最终状态),A4 PASS。
4. 检查缺陷闭环:发现的漏洞生成了 FIX-* 工单;高危未修复时结论=不通过且 chain_validate FAIL(A5/A6)。
5. **对抗有效性抽验(最有信息量)**:对记录中"防御成功"的 2-3 条用例,人工复核攻击构造是否真实(参数是否真的污染、并发是否真的并发)——防"假通过"。

**理想态**:六类全覆盖;SF/CC 逐条有实测;高危缺陷全闭环;抽验未见假通过。

**失败记录**:六类缺类 / SF-CC 未关联 / 并发是串行假测 / 抽验发现假通过 → 记录 + 归因(攻击用例模板不够 → 补模板;Agent 偷懒 → 考虑把用例生成固化为脚本)。

## 卡 5 · verify 环节(验证 C1/C2/D1/D3/D4/V10)

**时机**:adversarial 通过后,intent-verify 运行完成。

**步骤**:
1. 检查 verify-record:页面走查结果节存在且每页有真点证据(不是只写"已走查");V9 逐页核对通过。
2. 检查性能验证:三步法(放大→基准→压测)执行过,非空库计时。
3. 检查缺陷闭环:FIX-* 工单修复后做了定向复验(记录复验证据);V10 PASS。
4. 检查快照:验收脚本留存链路目录 snapshots/,标注"可能过期"。

**理想态**:四项全部落实;V10 PASS。

**失败记录**:走查缺页 / 性能空库计时 / 高危缺陷未修复却标通过 → 记录 + 归因(指引问题 → 改 SKILL;门禁缺失 → 加校验)。

## 卡 6 · 链级(验证 A2/E2)

**时机**:全链路结束后、交付判断前。

**步骤**:运行 chain_validate;检查输出矩阵每行的含义(PASS/FAIL/跳过都要能解释);确认链路状态的判定与实际一致——FAIL 行是否真是缺陷,还是校验器误报(误报本身也是要记录的问题)。

**理想态**:全部 PASS,或每个 FAIL 都有对应的缺陷工单且用户知情。

**失败记录**:误报(校验器规则过严)→ 记录规则与场景,评估放宽;漏报(该 FAIL 没 FAIL)→ 最高优先级,补校验规则。

---

## 归因三分类(每次验证失败必须归因,直接决定优化方向)

| 归因 | 判定标准 | 优化动作 | 优先级 |
|---|---|---|---|
| **校验器缺口** | 产物不合规但校验器 PASS(规则缺失或覆盖不足) | 把约束下沉为校验器规则——最高性价比,规则防线唯一可靠 | P0 |
| **SKILL 指引不够** | Agent 遵守了指引但产出仍不达标(指引缺步骤/缺底稿/粒度太粗) | 改 SKILL 规则、补模板、补方法论底稿 | P1 |
| **Agent 违反指引** | 指引明确清晰但 Agent 未执行 | 加强校验器拦截(指引对这类 Agent 不可靠)或在指引中增加自检清单 | P0(说明该约束必须下沉校验器) |

**方向判断信号**:同一张卡连续 2 个项目验证失败 → 该卡升级 P0;三类归因中"校验器缺口"占比最高 → 说明 SKILL 文字指引整体不可靠,体系重心应继续向校验器倾斜;"Agent 违反"占比高 → 考虑环节自动化(把 Agent 自由度收窄为填表)。
