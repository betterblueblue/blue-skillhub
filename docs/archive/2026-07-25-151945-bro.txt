● CI = Continuous Integration，持续集成。说白了就是：你每次往 GitHub 
  推代码，GitHub 自动帮你跑一遍检查，跑失败就标红提醒你。

  你这个仓库里就有一个，文件在 .github/workflows/eval-checks.yml。它的规则是：

  on:
    pull_request:
    push:
      branches:
        - master

  意思是「有人提 PR 或者往 master 推代码时，就触发」。触发以后 GitHub
  会临时开一台 Ubuntu 机器，装好 Python 3.11，然后按顺序跑这些检查：

  1. 把 eval/real-projects 下所有 JSON 解析一遍（防止有语法坏的 JSON）
  2. 跑 validate_real_projects.py（校验测评矩阵结构）
  3. 跑 impact / pathfinder / intent-anchor 的校验脚本单测
  4. 跑各 skill 的 tests/run.sh
  5. 检查模板同步
  6. 检查每个 SKILL.md 的 frontmatter 字段齐不齐

  任何一步退出码非 0，这次推送就在 GitHub 页面上显示一个红叉。

  你为什么会加这个

  ▎ 背景：2026-07-04 加 lazy-trap / scenario_type 那批改动引入了 4 个解析失败的

  他说对的部分

  「前期跟 AI 聊好技术方案，代码质量就高」——这个观察成立，但因果关系不是「聊得久
  」，而是约束有没有落成文字。同一份思考量，写进 spec 文件的和留在对话里的，效果
  差很远：留在对话里的约束会随上下文丢失，写进文件的每轮都能被重新读到。你仓库
  README 第 5 行说的就是这件事。

  「思考时间久意味着可能过度设计」——这个反思很准，而且原因比他想的更具体。你把思
  考力度拉满，模型会去穷举边界条件，而穷举出来的边界它没法判断哪些是现实的。它不
  知道你们线上 QPS 多少、这个字段有没有历史脏数据、这个分支三年会不会走到一次。
  所以它只能全部保住，代价就是引入抽象。

  他判断错的一处

  「都测不出
  bug，有点慌」——该慌，但不是因为「太顺了不真实」这种玄学，而是因为测不出 bug 
  不构成质量证据。测试没抓到，可能是方案确实好，也可能是测试只覆盖了主流程。这两
  种情况从「零 bug」这个结果上完全看不出区别。他现在只有一个数据点（测试同事的主
  观感受「比去年少」），没有覆盖率、没有边界用例清单，这时候「慌」是对的，但下一
  步动作应该是去看测了什么，而不是继续琢磨方案怎么聊。

  关于多模型互 review

  他同事的建议方向对，但「让 A 和 B 互相 review」这个做法本身有个坑，你在律刃第
  9 条里已经写过了：没有成功标准的 review 
  会变成重新设计。两个模型互评，各自都能挑出一堆「可以更好」的点，来回几轮方案越
  来越大，反而是他想避免的过度设计的另一条路径。

  要让 review 真的收敛，得给它三个东西：

  - 本轮目标和不处理的范围——不然它会把整个方案重新想一遍
  - 只接受能指出具体位置和实际影响的问题——「这里扩展性不足」不算，「这个接口改了
  之后 X 处调用方要同步改，方案里没写」才算
  - 必须给一个明确结论——你律刃第 9 条末尾那四选一（必须修复 / 可以进入验证 /
  验证通过停止 / 有已知限制但不建议继续优化）。没有这个强制结论，模型永远会留一
  句「还可以进一步优化」，你就永远不知道该不该停。

  他提到「要选自主意识强的模型」，这个变量存在但不是主要的。比让模型「敢反对」更
  有效的是给它一个明确的对立角色：「你的任务是找出这个方案里为不会发生的场景付出
  的复杂度代价，逐条指出位置」。这样问，服从性高的模型也会给出反对意见，因为反对
  就是它被派的活。

  - 可追溯——两个模型分别说了什么、你最后采纳了哪条，git 里留得下
  - 第三个模型能接上——他楼下有人提「AB 互认之后给 C
