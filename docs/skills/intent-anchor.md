# IntentAnchor（意图锚定）

> 把还没成形的产品想法追问成一份可交接的 `INTENT.md`：解决什么问题、要哪些能力、哪些不能妥协、每项决定由谁拍板。

运行：`/intent-anchor`（手动触发）｜技能本体：[skills/intent-anchor/](../../skills/intent-anchor/)

## 它做什么

- 通过对话澄清意图，产出 17 节结构的 `INTENT.md`：一句话意图、场景类型、能力与决策、不可妥协项、验收路径、性能要求、安全要求、术语表等。
- 按三种场景分流取证：全新项目（0→1）、系统转换（X→Y，必须盘点源系统能力）、已有系统新增能力（只读相关模块）。
- 每项能力用稳定 ID（C01、C02……）记录，决策只允许三个来源：用户明确确认 / 用户授权模型决定 / 模型建议（未确认）。
- 区分"确认"的语义：用户说"你定、都行"是授权模型选择，不是用户本人赞同；`放弃` 必须用户本人确认；用户原话逐字摘录。
- 支持轻量 / 标准两档：轻量档只减文档厚度和确认次数，验收路径、证据、结构校验一概不降级。

## 什么时候用

- 0→1 新产品开工前，想法还说不清给谁用、解决什么问题。
- 系统转换前，需要盘点源系统哪些能力保留、推迟、放弃。
- 已有系统要加新能力，但目标和取舍还模糊。
- 不需要用：已有明确 PRD 或可执行规格（直接进后续流程）；已有系统的改动需求已经清楚"改什么"（直接用 impact）。

## 常见问题

**INTENT.md 和 PRD 有什么区别？**
INTENT.md 记录"要什么、不要什么、谁拍板的"；PRD 记录"具体怎么做才算做好"。意图先于方案，所以 anchor 在 PRD 之前。

**我说了"你定"，最后记录成什么？**
记录为"用户授权模型决定"，模型必须说明选择和理由；这类决策不能作为不可妥协项的依据。

**校验 FAIL 是不是说明内容错了？**
不是。`intent_validate.py` 只检查结构、字段关系和确认记录，不验证事实真假；FAIL 只说明文件不满足结构契约。

**轻量档会少掉什么？**
只少文档厚度和确认次数。要加数据库、权限或对外 API 时会强制升为标准档，且只升不降。

## 用对了是什么样子

- `INTENT.md` 通过结构校验，没有任何 `待确认` 项残留。
- 每条验收路径都能独立写成"我做 X，看到 Y"，用户可感知的能力至少出现在一条路径里。
- 每项决策都能指出决策来源，用户原话逐字在案，没有补写或改写。
