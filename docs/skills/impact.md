# ImpactRadar（变更影响分析）

> 面向已有系统：把模糊的变更意图通过靶向提问变成基于证据的影响分析，再在逐步确认下实施。写操作必须绑定 Step 编号确认，模糊回答不算授权。

运行：`/impact`（模型可自动触发）｜技能本体：[skills/impact/](../../skills/impact/)

## 它做什么

- 五个阶段：意图捕获 → 技术栈检测与上下文发现 → 风险预判 → 苏格拉底式探索与定级 → 文档输出与逐步执行。
- light / full 两档：小改动走一页摘要，复杂变更走三份分析文档 + 状态文件；判定基于证据，由用户复核确认。
- 写入门禁：所有写操作绑定 `确认 Step N`；模糊确认（"嗯""可以""都行""继续"）、历史授权、测试通过结果一律不算；提问后不等待回答继续执行（假提问）不构成确认。
- 高风险拦截清单：DROP/TRUNCATE、无 WHERE 的 DELETE、改 ORM schema 文件、删对外接口、改权限标识等，命中即停，单独确认。
- 技术栈规则外置：Java/Spring/MyBatis、Node/Express/Prisma、Python/FastAPI、Go/Gin/GORM、Next.js、Nuxt 等在 `profiles/`，数据库在 `db-adapters/`，加新栈只需加一个文件。
- DB 只读纪律：schema 发现阶段只允许 SELECT/SHOW/DESCRIBE；DDL/DML 默认生成脚本不直接执行，生产库禁止 agent 直接执行。

## 什么时候用

- 已有系统上新增功能、修 bug、重构，尤其是改了怕出连锁反应的地方。
- 破坏性请求（删字段、删接口、批量替换）必须先走它的影响发现，不能直接动手。
- 不需要用：从 0 到 1 建新系统（走 intent-chain）；项目完全不熟（先跑 pathfinder，不跑也行，impact 会自己做发现）。

## 常见问题

**为什么改个字段也要确认这么多步？**
门禁的重量和变更的风险挂钩：轻量档和快速通道小改动只要一页摘要加少量确认；确认真正的目标是"AI 想动手时，你明确知道它要动什么"。

**"你定，随便"之后它会自己选吗？**
不会静默选。走降级流程：选代码现状为默认、回显依据、记入已确认事实；高风险岔路（DB 契约、权限、枚举、删除）不可委托。

**和我项目里的 code review 有什么关系？**
impact 管动手前和动手中的影响面；代码评审管动手后的质量。两者不互替。

**怎么防止它把没做过说成做完了？**
验证声明必须附原始命令输出（含退出码），只写结论不附输出等于未验证；执行记录由校验器检查。

## 用对了是什么样子

- `impact_validate.py` 全部 PASS，结果记入 `_active-state.md`。
- 每次写代码前，对话里能看到你亲口回复的 `确认 Step N`。
- 中断恢复后，它先复述 pending 步骤和目标文件现状，等你新的确认才继续写。
- 破坏性变更在动手前看到了破坏面回显和兼容方案。
