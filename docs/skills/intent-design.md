# IntentDesign（技术方案设计）

> 读取 `INTENT.md` 和 PRD，产出两份文档：`architecture.md` 写全局架构决策（分层、模块边界、技术选型、数据流、额外结构与假设），`design.md` 写每个保留能力在架构里怎么落地。

运行：`/intent-design`（手动触发）｜技能本体：[skills/intent-design/](../../skills/intent-design/)

## 它做什么

- 全局层和能力层分开成两份文档，各有固定章节结构，`design_validate.py` 交叉检查模块引用、能力覆盖、假设合规性、非功能性要求承接、数据设计完整性。
- 把技术选型理由和"额外结构与假设"显式写出来，供后续阶段核对漂移。
- **假设表带一条体验岔路**：标"无依据"的条目若要亲手体验才能拍板（比如两种交互流程哪个顺手），主动建议做一个一次性小样（demo 页面或小脚本）让用户体验后再定——小样用完即弃，不进交付；没装任何原型工具也能按规则现场做。
- 模块边界设计有一套普通话自查判据（`references/deep-module.md`）：调用方学几个入口、得到多少行为，删除测试识别浅转发层。
- 轻量档允许薄写法（架构概览两三句、各表每行一条），章节和表结构不变。
- 设计中发现需要数据库、权限或对外 API 时，触发升档单向规则：停下来告知用户升为标准档。

## 什么时候用

- PRD 通过校验之后、拆分工单之前。
- 前置条件：`INTENT.md` 和 `prd.md` 都已通过各自校验器。
- 不需要用：改动已有系统（那是 impact 的领地，它自带轻量/全量分析文档）。

## 常见问题

**为什么拆成两份文档？**
全局决策（选型、分层）和能力落地（某个功能怎么实现）变更频率和读者都不同；混在一份里，改一个功能要重读全部架构。

**"额外结构与假设"是什么？**
设计里新增的、需求没直接要求的东西（引入消息队列、加缓存层等）。显式登记后，验收阶段能检查"有没有偷偷加上需求外的东西"。

**选型可以直接替用户定吗？**
常规选型可以（记录依据），但涉及意图文件里不可妥协项的取舍必须回到用户。

**设计上拿不准的方案，只能靠文字想象吗？**
不是。假设表里标"无依据"的条目，如果体验一下就能拍板（两种交互流程、两种状态流转），intent-design 会主动建议做个一次性小样让你亲手点一遍再定，小样不进交付。

## 用对了是什么样子

- `design_validate.py` 校验通过，能力覆盖检查无缺口。
- INTENT.md 里的性能、安全要求被承接进设计，没有凭空消失。
- 每个设计项有编号，后续实施文档能引用它做映射。
