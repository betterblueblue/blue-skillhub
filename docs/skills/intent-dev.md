# IntentDev（按工单开发）

> 按依赖顺序逐个开发工单，每个工单走 TDD 红绿循环；每条验收标准都要有真实运行证据才能标完成，完成后写 `dev-record.md` 交接验收。

运行：`/intent-dev`（手动触发）｜技能本体：[skills/intent-dev/](../../skills/intent-dev/)

## 它做什么

- 按工单依赖顺序开发。新功能工单走 Red-Green-Refactor；修 bug 工单必须先写复现测试（先修后补测试不允许标 done）；纯样式/配置工单直接实现、以运行结果为证。
- **测试入口清单**：写测试前先列出功能对外的入口（页面操作、接口、公开方法）并给用户确认，测试只从入口进、不调内部私有方法——内部代码以后怎么重构，测试都不用跟着改。
- 验证分三级：V0 未验证、V1 代码审查、V2 实际运行通过。**标 V2 必须附真实命令输出，没有输出视为 V1 冒充**，不允许标 done。
- 验证手段按优先级：项目自带构建/测试命令 → 直接运行项目入口 → 针对验收标准写最小验证脚本（临时脚本不写入项目）。
- AFK 工单可批量授权，但每完成一个垂直切片必须停下来给用户看实际效果、得到显式确认才继续。
- 全部工单完成后运行 `dev_validate.py` 交叉检查，然后交接给 intent-verify 和 intent-adversarial；adversarial/verify 产出的 FIX-* 缺陷工单由它承接修复。

## 什么时候用

- 工单拆分完成之后，逐单开发时。
- 前置条件：INTENT.md、PRD、工单、architecture.md、design.md 五者齐且通过校验。
- 单独使用受限：五文件缺一不可是硬门禁，不满足时请走 impact 或直接开发。

## 常见问题

**项目没有测试环境怎么办？**
按"验证命令来源"的优先级找替代手段（直接跑入口、写最小验证脚本）；实在不行降级 V1，默认不能标 done，除非用户明确确认接受。

**可以并行开发多个工单吗？**
默认串行。用户明确要求且环境支持时，按 `Blocked by` 分波次并行，共享文件由每波结束后的集成步骤统一改，波间全量回归。

**为什么它不做端到端验收？**
工单级验证和路径级验收是两件事；自己开发自己验收容易both当运动员和裁判，所以验收交给 intent-verify。

## 用对了是什么样子

- `dev-record.md` 里每条 Then 都有验证等级和证据，V2 条目能翻出真实命令输出。
- 修 bug 工单能找到对应的复现测试。
- 全部工单标 done，`dev_validate.py` 通过，工单编号与 issues.md 交叉核对一致。
