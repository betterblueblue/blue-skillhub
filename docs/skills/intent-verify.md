# IntentVerify（端到端验收）

> 所有工单完成后做整体验收：先跑全量测试确认老功能没坏，再按 INTENT.md 的验收路径逐条真实走通，核对保留能力有没有被偷偷丢掉或加上。工单级验证检查零件，这一步把零件装成整机通电试跑。

运行：`/intent-verify`（手动触发）｜技能本体：[skills/intent-verify/](../../skills/intent-verify/)

## 它做什么

- 全量测试回归：确认开发过程没有改坏既有功能。
- 逐条走验收路径：INTENT.md 第 14 节的每条路径都要端到端走通，证据用 V3 等级（真实截图、真实运行产物）。
- 漂移核对：每个保留能力检查有没有实现或验证证据；有没有未经确认的新增、替换、遗漏。
- 性能与安全要求复核：INTENT.md 有要求时逐条验证；页级还原项目（INTENT 第 17 节有页面清单）逐页核对。
- 产出验收记录和缺陷清单；链路末尾运行 `chain_validate.py` 做链级校验，任一 FAIL 不得宣告链路走完。

## 什么时候用

- intent-dev 全部工单标 done 之后、交付之前。
- 前置条件：INTENT.md、PRD、工单、dev-record、architecture.md、design.md 六者齐且通过校验。
- 恶意输入和高并发场景不在本环节（那是 intent-adversarial 的事）。

## 常见问题

**工单都验过了，为什么还要整体验收？**
工单验证只覆盖各工单的验收标准；路径级的衔接（A 工单的输出能进 B 工单的输入）、能力漂移、老功能回归，只有整机试跑才能发现。

**"漂移"指什么？**
用户确认过的东西在下游被悄悄丢掉，或者没确认过的东西被悄悄加上。验收时拿 INTENT.md 逐项核对，两头都要查。

**走查证据长什么样？**
真实操作产生的截图、命令输出、页面状态，不是"已验证"的结论性描述。

## 用对了是什么样子

- 每条验收路径都有可核对的走查证据，UI 路径附真实截图。
- 全量测试绿；INTENT.md 的性能、安全要求逐条有验证结论。
- `chain_validate.py` 全部 PASS，漂移核对没有未解释的差异。
