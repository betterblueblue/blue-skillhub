# IntentAdversarial（对抗性验证）

> 工单开发完成后，把系统当敌人打：安全攻击实测、并发一致性断言、性能压测三步法。发现的缺陷生成 FIX-* 工单，阻止带病交付。

运行：`/intent-adversarial`（手动触发）｜技能本体：[skills/intent-adversarial/](../../skills/intent-adversarial/)

## 它做什么

- **安全攻击实测**：六类用例逐类处理——垂直越权、横向越权、跨角色越权、未授权访问、业务逻辑攻击（重复支付、负数参数、并发库存）、暴力破解与注册提权。项目里没有某类攻击面时（如单用户 CLI 没有登录和角色）写「不适用」并附依据。每条安全要求（SF 编号）至少被一类覆盖，每个用例记录请求、响应和数据库副作用核查。
- **并发一致性断言**：每条并发要求（CC 编号）逐条攻击实测，比如"库存=1 时 N 并发支付，成功 ≤ 1"——超卖、重复抢单这类缺陷串行测试永远抓不到。
- **性能压测三步法**：有性能要求（PF 编号）时，先把数据放大到真实规模（空库压测无意义），再采集基准（avg/p50/p95），最后并发压测记录 rps/p95/5xx。
- 只攻击不修复：缺陷生成 FIX-* 工单交 intent-dev 修，修完回到本环节定向复验。

## 什么时候用

- 所有工单标 done 之后、宣告交付之前；INTENT.md 里有 SF 或 CC 要求时是硬门禁。
- 动手前先和用户确认目标环境（服务地址、数据库）不是生产环境：攻击会锁账号、灌测试数据、尝试越权写。
- INTENT.md 没有安全/并发要求、系统也没有对应攻击面时，各类写「不适用」并附依据，很快就能走完。
- 日常小改动不需要全套流程，用 impact 的"风险分级定向回归"即可。

## 常见问题

**代码里有校验逻辑，还要实测吗？**
要。实战评测证明静态确认（"代码里有校验"）对注册提权、缺失归属校验的命中率是零——只有真实请求打过去才知道校验生不生效。

**和 intent-verify 有什么区别？**
intent-verify 验证"正常用户走路径走得通"，本环节验证"恶意输入和高并发打不穿"。一个管能不能用，一个管扛不扛得住。intent-verify 会直接引用本环节的实测结果，不再重跑一遍。

**测试数据怎么准备？**
按 INTENT 性能要求推导规模灌入种子数据，跑完恢复干净演示态；攻击身份按项目的角色构造，每个角色至少一个账号，测横向越权的角色准备两个同角色账号。

## 用对了是什么样子

- 每条 SF 和 CC 要求都有对应的实测用例和结果记录，不是"已覆盖"一句话。
- 六类每类都有一行：实测结果，或「不适用」加依据。
- 数据库副作用核查在每次攻击后执行过（调完接口查库确认数据没变）。
- 发现的缺陷全部生成 FIX-* 工单并闭环，复验通过后才放行交付。
